Cross-Site Scripting (XSS)

Cross-Site Scripting (XSS) is a web vulnerability that allows an attacker to inject malicious JavaScript into a web application.

The injected script executes in the victim's browser within the context of the vulnerable website.

Why Is XSS Dangerous?

An attacker may be able to:

• Steal session cookies

• Perform actions on behalf of users

• Redirect users to malicious websites

• Modify page content

• Capture keystrokes

How XSS Works

1- The attacker injects JavaScript into a vulnerable application.

2- The application returns the malicious script to users.

3- The victim's browser executes the script.

4- The attacker gains access to sensitive information or performs malicious actions.

Example

User input:

<script>alert('XSS')</script>

Vulnerable page output:

<h1>Welcome</h1>
<script>alert('XSS')</script>

The browser executes the JavaScript code.

Types of XSS

Stored XSS

The malicious payload is stored on the server.

Examples:

• Comments

• User profiles

• Forum posts

Every user viewing the page executes the payload.

Example
<script>alert('Stored XSS')</script>
Reflected XSS

The payload is immediately reflected in the response.

Commonly found in search pages and error messages.

Example URL
https://example.com/search?q=<script>alert(1)</script>

If the application reflects the input without sanitization, the script executes.

DOM-Based XSS

The vulnerability exists entirely in client-side JavaScript.

The server may never see the payload.

Example
document.getElementById("output").innerHTML =
location.hash;

An attacker may control the URL fragment and inject JavaScript.

Common Payloads

<script>alert(1)</script>
<img src=x onerror=alert(1)>
<svg onload=alert(1)>
<body onload=alert(1)>

Impact of XSS

• Session hijacking

• Account takeover

• Credential theft

• Defacement

• Phishing attacks

• Access to sensitive data

Finding XSS

Look for places where user input is displayed back to users.

Common targets:

• Search fields

• Comments

• User profiles

• Contact forms

• URL parameters

Example Test

Input:

test123

Check whether it appears in the response.

Then try:

<script>alert(1)</script>

Preventing XSS

Output Encoding

Encode user-controlled data before displaying it.

Input Validation

Validate and sanitize user input.

Content Security Policy (CSP)

Restrict which scripts can execute.

Example:

Content-Security-Policy:
default-src 'self'
HttpOnly Cookies

Prevent JavaScript from accessing session cookies.

Set-Cookie:
session=abc123; HttpOnly

What Should a Penetration Tester Check?

• Is user input reflected in the response?

• Is HTML encoding applied?

• Can JavaScript execute?

• Is CSP implemented?

• Are session cookies protected with HttpOnly?

• Does the application use dangerous functions such as:

innerHTML
document.write()
eval()

XSS Testing Workflow

1- Find user-controlled input.

2- Check whether the input is reflected.

3- Determine the HTML context.

4- Test XSS payloads.

5- Verify JavaScript execution.

6- Assess impact and exploitability.
