The command: This is 'sudo apt update' then 'sudo apt upgrade -y' used to update the package lists and then upgrade the system. The results mean: 76 packages available for upgrade, and the download of updates totaling approximately 578 MB — a routine system maintenance phase.

Command: sudo apt install apache2 -y Used to install the Apache2 web server. Result: Apache2 is pre-installed with the latest version (2.4.66-2ubuntu2.4) — no need for a new installation.

The commands: sudo systemctl enable apache2`then` start and `then` status are used to activate, start, and check the status of the service. Result: The service is active (running) successfully.

Link: http://192.168.81.130 Used to browse the website hosted on the victim. Result: Appearance of the default Apache2 page "It works!" — confirmation that the server is working without any customized content yet.

Commands (on the victim): cd /var/www/html, sudo rm index.html, then echo "..." | sudo tee ...to create: index.html, login.php, admin.php, upload.php, backup.zip. Used to build a fake test site with commonly targeted pages to simulate a realistic hacking scenario config.php.

Link: http://192.168.81.130/admin.php The result: "Admin Panel" appears — an exposed page with no visible protection or authentication.

Commands: sudo truncate -s 0 for my file /var/log/apache2/access.logand error.log then restart apache2. Used to dump Apache logs and then restart the service. Result: Service active only 29 seconds ago — Erasing directories/resetting before starting the test status

We begin the attack scenario to generate logs.

This command nmap -sV 192.168.81.130 is used to scan the machine after the web interface is running. The result: Two open ports — 22 (SSH) and 80 (Apache 2.4.66) — expands the attack surface.

Command: curl -I http://192.168.81.130 Used to fetch HTTP headers only. Result: 200 OK, Server: Apache/2.4.66 (Ubuntu) — Initial server fingerprint.

Command: gobuster dir -u http://192.168.81.130 -w /usr/share/wordlists/dirb/common.txt Used to discover hidden folders by automatic guessing. Result: Discovery admin.phpof index.html(200), and 403-protected paths ( .htaccess,,, .htpasswd) server-status— admin.php detected despite not being linked to any visible URL.

commands are used to manually verify the content of detected pages. The result: confirmation of the content of each page and the backup.zip file .curladmin.phplogin.phpupload.phpbackup.zip

strings curl on .env, phpmyadmin, config, test, admin are used to guess additional sensitive paths. The result: all 404 — no vulnerability here.

Commands: These are curl "login.php?id=1'"then curl "login.php?id=1 OR 1=1" used to test SQL injection by inserting a quotation mark followed by a consistently valid logical condition. The result: The first returned the normal page unchanged, while the second failed with a "Malformed input to a URL function" error due to uncoded spaces in the URL—a technically incomplete attempt.

Command: LOG=/var/log/apache2/access.log Used to define a shell variable with the path to the access log file to facilitate the following commands.

Command: awk '{print $1}' $LOG | sort | uniq -c | sort -nr Used to count the frequency of each IP address in the log. Result: 4635 requests from 192.168.81.129 (the attacker) versus only two requests from ::1 — almost all activity from a single machine at high intensity.

Command: awk '{print $4,$1,$6,$7,$9}' $LOG Used to display time, IP, method, path, and response code. Result: A clear sequence of initial nmap scans followed by a massive gobuster wave ( .bash_history,,, ...) .git/HEAD, _adminmostly 404.

Command: awk '{print $7}' $LOG | sort | uniq -c | sort -nr Used to count the repetitions of each path (URL). The result: /(5 times), /test( /sdktwice each) /phpmyadmin, /admin.phpthen hundreds of paths at once.

The same results were completed — digital paths ( /1000... /0) and sensitive files ( .ssh, .bash_history, .env, .git/HEAD) with one iteration of each.

Command 25awk '$9==404 {print $4,$1,$7}' $LOG : Used to display only failed (404) requests. Result: A long list of failed access attempts to random paths and directories.

Continuation of the same 404 results — more failed paths ( /xyzzy, /yahoo... up to the last XSS attempt).

Command awk '{print $9}' $LOG | sort | uniq -c : Used to count the distribution of HTTP response codes. The result: 15 requests (200), 4 requests (403), 4618 requests (404) — over 99% of the activity were failed attempts.

Command grep -Ei 'admin|login|upload|backup|config|\.env|phpmyadmin' $LOG : Used for focused searching of common sensitive keywords. Result: Dozens of attempts to guess "admin" paths in various formats (404), except for admin.phpthe one that returned 200.

Command grep -i gobuster $LOG : Used to isolate all requests that specifically used the GoBuster tool. Result: A detailed view of the GoBuster scan waveform ( .bash_history, .htaccess, .git/HEAD, _admin...), mostly 404 and some 403.

Command: grep -i curl $LOG Used to isolate manual requests that used curl only. Result: Clear sequence of manual requests: HEAD /(200), admin.php(200), login.php(200), upload.php(200), backup.zip(200), failed attempts ( .env, phpmyadmin, config, test, admin), SQLi attempt (200), XSS attempt (404).

Command awk '$9==404 {print $1}' $LOG | sort | uniq -c | sort -nr : Used to count failed (404) requests grouped by IP address. Result: 4618 failed requests from address 192.168.81.129 — confirming that all failures originated from the same attacker.

Command awk '{print substr($4,2,17)}' $LOG | sort | uniq -c : Used to group requests by minute (extracting the abbreviated time signature). The result: Time signature of activity — a huge concentration at 03:55 with 4617 requests (gobuster wave), while the rest of the times (02:23 , 02:24 , 03:57 and beyond) were at a rate of only one or two requests — showing that the gobuster attack was very fast and intense over approximately one minute, while the reconnaissance and manual exploitation were time-separated.
