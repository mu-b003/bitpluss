Privilege Escalation Investigation

This task can be performed practically in an isolated virtual lab if you do not have one you can set up a virtual lab using the provided link.

Command: `sudo adduser Afreen` This command is used to create a new user named "Afreen" on the system. The output indicates that the system warned that the home directory already exists and would not be recreated, and also warned that the password was too short (fewer than 8 characters); however, it allowed the process to proceed, and the user was successfully created.

Command: `sudo truncate -s 0 /var/log/auth.log` This command is used to completely clear the contents of the authentication log file and set its size to zero. The output showed no error messages, indicating that the previous logs were successfully erased. Command: `sudo systemctl restart ssh` This command is used to restart the SSH service. The output showed no errors, indicating that the service restarted successfully. Command: `sudo systemctl status ssh` This is used to check the service status after the restart. The output indicates that the service has been "active (running)" for just 14 seconds and is listening on port 22 (IPv4 and IPv6).

Command: `ip a` This command is used to display details about network interfaces and IP addresses. The results indicate that the machine has a local IP address of 192.168.81.129 on the `ens33` interface—which is the IP address of the victim machine itself.

At this stage we will execute an attack aimed at generating logs.

Command: nmap -sV 192.168.81.129 This command is used to scan the target machine and identify open ports, services, and their versions. The results indicate that the machine is active and has only one open port: port 22 (SSH service running OpenSSH 10.2p1 Ubuntu), with the operating system identified as Linux (VMware).

Command: `ssh Afreen@192.168.81.129` This command is used to connect to the target machine via SSH using the "Afreen" account. The resulting output indicates a successful login, noting "Last login... from 192.168.81.128"—meaning this is a repeat connection from the same attacker. Commands: `hostname`, `whoami`, `id`, `groups`, `pwd` These are used to determine the session identity and privileges. The results indicate: the user is "Afreen" on the victim machine, located in the `/home/Afreen` directory, and is a member of only the "Afreen" and "users" groups.

Command: `sudo -l` Used to check available `sudo` privileges. Result: Explicit denial ("Afreen may not run sudo") — no administrative privileges.

Command: `su root` Used to attempt to switch directly to the root account. Result: "Authentication failure" — the attempt failed.

Command: `cat /etc/shadow` Used to attempt to read the encrypted password file (a highly sensitive file). Result: "Permission denied" — the attempt was rejected.

Command: `cd /root` Used to attempt to enter the `root` directory. Result: "Permission denied" — the attempt was rejected.

Command: `sudo ls /root` This is used to attempt to list the contents of the `/root` directory via `sudo` (despite knowing that the necessary permissions are lacking). Result: A custom, sarcastic refusal message from the system: "sudo: I'm sorry Afreen. I'm afraid I can't do that." This is a custom `sudo` message (replacing the default one) configured by the administrator to reject this specific user with a humorous reference to the movie *2001: A Space Odyssey*. Command: `find / -perm -4000 -type f 2>/dev/null` This command is used to search for all files with the SUID permission bit (permission bit 4000) set. These files execute with the privileges of their owner (often `root`), regardless of who runs them. This is a very common technique in privilege escalation used to identify potentially exploitable vulnerabilities. The output lists the files with the SUID bit set: `/usr/bin/pkexec`, `/usr/bin/umount`, `/usr/bin/sudo.ws`, `/usr/bin/passwd`, `/usr/bin/chfn`, `/usr/bin/gpasswd`, `/usr/bin/mount`, and `/usr/bin/su`. While this is generally a standard list, the attacker was examining it to find any known vulnerability that could be exploited to gain `root` access.

Command: `sudo -l` Used again to check sudo privileges. Result: The same refusal as before—"Afreen may not run sudo". Command: `exit` Used to end the session. The resulting output indicates logging out and completely terminating the SSH connection ("Connection to 192.168.81.129 closed").

We begin the analysis scenario here.

Command: `grep sudo /var/log/auth.log` Used to search for all instances of `sudo` usage on the system. The results indicate that all `sudo` usage originated solely from the legitimate user `soc-lab` (to execute `systemctl restart/status ssh`); in other words, Afreen never successfully used `sudo`. Command: `grep "su:" /var/log/auth.log` Used to search for attempts to use the `su` command. Result: A single line documenting a failed attempt by Afreen to escalate privileges to `root` via `su` ("authentication failure... ruser=Afreen... user=root").

Command: `grep "Afreen" /var/log/auth.log` Used to search for all events specifically associated with the Afreen account. The results tell the story: a successful SSH login and the opening of two sessions (numbers '6' and '7'), a failed attempt to `su` to root—followed by "FAILED SU (to root) Afreen on pts/1" (further confirming the failed privilege escalation attempt)—and finally, disconnection and session closure. Command: `grep "COMMAND=" /var/log/auth.log` Used to display all commands executed via `sudo`. The result: only standard administrative `soc-lab` commands (SSH restart/status). Command: `grep sshd /var/log/auth.log` Used to search for all SSH service events. The results confirm the same sequence: service startup, a prior disconnected connection from the same address, a successful login by Afreen, and finally, a normal disconnection initiated by the user.

Command: `grep "Afreen" /var/log/auth.log | head -1` Used to display only the first line. Result: The first event was a successful login ("Accepted password for Afreen"). Command: `grep "Afreen" /var/log/auth.log | tail -1` Used to display only the last line. Result: The last event was the session closing ("session closed for user Afreen"). Command: `grep "Afreen" ?var/log/auth.log` (contains a typo with a question mark instead of a forward slash) Used for the same purpose but with an incorrect path. Result: An error message "No such file or directory" because the path is incorrect. Command: `grep "Afreen" /var/log/auth.log` (path corrected and re-executed) Result: The same complete and correct list of Afreen-related events as in p8.

Command: `grep "COMMAND=" /var/log/auth.log` (Repeated) Used to display all executed `sudo` commands. Result: Only the administrative `soc-lab` commands. Command: `grep "session opeded for user root" /var/log/auth.log` (contains a typo: "opeded" instead of "opened") Used to search for opened `root` sessions; however, due to the typo, no lines matched. Result: No output (because the misspelled word does not match the actual text in the log).

Command: `last root` Used to display the login history specifically for the `root` account. Result: No results (only the message "wtmpdb begins..."), meaning the `root` account was never used for a direct login during this period—further evidence that the attacker's attempts to access `root` all failed.

Command: `grep -oP '(?<=from )(\d{1,3}\.){3}\d{1,3}' /var/log/auth.log | sort -u` Used to extract all unique IP addresses appearing after the word "from" in the log. Result: A single address, 192.168.81.128—confirming that all suspicious activity originated from one source.

Command: `grep -E "Accepted|Failed" /var/log/auth.log | awk '{for(i=1;i<=NF;i++) if($i=="for") print $(i+1)}' | sort -u` Used to extract the target username from login attempts (successful or failed). Result: Only "Afreen"—confirming that a single account was targeted.

Command: `grep "Authentication failure" /var/log/auth.log` Used to search for any other authentication failures in a different format. Result: No output (no additional lines matched this specific format, unlike the `su` case—which appeared in previous searches—that used the lowercase "authentication failure").
