How SOC Analysts Detect Suspicious Activity

How SOC Analysts Detect Suspicious Activity

SOC analysts deal with a large number of security events every day. Most events are normal activities, so the analyst's job is not to investigate everything. Instead, the analyst looks for unusual patterns, suspicious behavior, and events that require further investigation.

The process can be understood as:

Event → Detection → Alert → Triage → Investigation → Finding

What Is a Security Event?

A security event is a recorded activity generated by a system, application, network device, or security tool.

Examples include a user logging in, a failed authentication attempt, a process starting, a DNS request, a firewall connection, or a file being created.

For example:

User: admin
Action: Login
Source IP: 192.168.1.25
Result: Failed

This is an event. By itself, it does not necessarily mean that an attack is happening.

From Event to Detection

Security platforms use detection rules and other techniques to identify events or patterns that may be suspicious.

A simple detection could look for repeated failed authentication attempts from the same source.

Example: 20 failed login attempts against one account within five minutes.

One failed login may be normal. A large number of attempts in a short period may deserve attention because the pattern provides more context.

What Is an Alert?

When activity matches a detection condition, a security platform can generate an alert.

An alert tells the SOC analyst that specific activity has been identified as potentially suspicious.

For example:

Alert: Multiple Failed Login Attempts

The alert may contain information such as the username, source IP address, destination system, timestamp, number of attempts, and detection rule that triggered the alert.

An alert is not automatically proof of an attack. It is a starting point for analysis.

Alert Triage

After receiving an alert, the analyst performs triage. Triage is the initial process of determining what the alert means and whether it requires further investigation.

The analyst may ask:

Who performed the activity?

What happened?

When did it happen?

Where did it originate?

Which system was affected?

Is the activity expected?

Are there related events?

The analyst uses this information to understand the context of the alert.

Checking the Context

Context is one of the most important parts of security analysis.

Consider a failed login from an employee's normal device during working hours. This may be explained by a simple password mistake.

Now consider hundreds of failed logins from an unfamiliar source followed by a successful login to an administrative account. The same type of event now requires much more attention.

The individual events may look similar, but the surrounding context is different.

Looking for Related Events

Analysts rarely investigate an alert in isolation. They often search for related activity before and after the event.

For example:

Failed logins → Successful login → Privileged activity → New process → External connection

Connecting these events can provide a clearer picture of what happened.

This is commonly called event correlation.

Investigating the User

The analyst may examine the account involved in the alert.

Useful questions include:

Is this a normal user?

Does the user normally access this system?

Does the user normally work at this time?

Was the account recently created or modified?

Did the account receive additional privileges?

Were there successful logins after multiple failures?

Understanding normal account behavior can help analysts identify unusual activity.

Investigating the Device

The analyst may also investigate the affected endpoint or server.

This can include checking running processes, recently created files, command execution, network connections, user activity, and other available endpoint data.

For example, if a suspicious login was followed by an unusual PowerShell process, the analyst may investigate the command that was executed and determine what happened afterward.

Investigating Network Activity

Network information can provide additional context.

An analyst may examine:

Source and destination IP addresses, ports, protocols, DNS requests, external connections, and connection frequency.

For example, an endpoint that suddenly begins making repeated connections to an unfamiliar external destination may require additional investigation.

However, unusual network activity does not automatically mean malicious activity. The analyst should combine network evidence with other information.

Building a Timeline

A timeline helps the analyst understand the sequence of events.

For example:

10:01 — Multiple failed logins

10:03 — Successful login

10:05 — Privileged session created

10:07 — PowerShell process started

10:09 — External network connection detected

A timeline can reveal relationships that are difficult to see when events are viewed separately.

Determining Whether Activity Is Suspicious

After collecting evidence, the analyst evaluates the activity.

The analyst may determine that the activity is:

Benign: The activity is legitimate and can be closed or documented.

Suspicious: The activity cannot yet be explained and requires additional investigation.

Confirmed malicious activity: Sufficient evidence indicates that the activity is associated with a security incident.

The exact classification process varies between organizations.

Why Analysts Should Not Jump to Conclusions

A suspicious event is not automatically an attack.

For example, repeated failed logins could be caused by a user entering the wrong password, a misconfigured application, an automated service, or malicious activity.

The analyst's responsibility is to examine the available evidence and determine which explanation is supported by the investigation.

This is why SOC analysis is based on evidence, context, and correlation.

From Alert to Investigation

The complete process can be summarized as:

Event — A system records activity.

Detection — A rule or security mechanism identifies potentially suspicious activity.

Alert — The SOC is notified.

Triage — The analyst reviews the alert and its context.

Investigation — Related logs, users, devices, and network activity are examined.

Finding — The analyst documents what the evidence shows and determines the appropriate next step.

Key Takeaway

SOC analysts do not simply respond to alerts. They turn individual security events into meaningful investigations by looking at patterns, context, timelines, and related evidence.

The process can be remembered as:

Event → Detection → Alert → Triage → Investigation → Finding

Understanding this process is one of the foundations of SOC work and provides the basis for learning deeper topics such as SIEM, log analysis, threat detection, incident response, and threat hunting.
