What is Suspicious DNS Activity?

Suspicious DNS activity refers to DNS behavior that appears unusual, unexpected, or inconsistent with the normal activity of a system or network. DNS is essential for normal communication, so a large amount of DNS traffic is expected in most environments. The goal of an investigation is therefore not to find unusual DNS requests and immediately label them malicious, but to determine whether the activity has a reasonable explanation.

Suspicious DNS activity can involve unusual domains, repeated queries, unexpected query volumes, random-looking subdomains, frequent failed lookups, or DNS requests generated by systems that normally have very limited network activity. These indicators become more meaningful when they are correlated with endpoint and network events.

Why Investigate Suspicious DNS Activity?

DNS can provide an early indication that a system is communicating with an unfamiliar service or potentially compromised infrastructure. Malware may use DNS to locate remote infrastructure, resolve domains used for command and control, or generate repeated requests as part of its communication process.

Investigating DNS activity can help a SOC Analyst identify potentially compromised hosts, unusual applications, unauthorized communication, malware-related behavior, and other security events that may not be obvious from a single endpoint or network log.

Start With the Source Host

The first step is to identify which system generated the suspicious DNS query. Record the source IP address, hostname if available, and the type of system involved.

A DNS request from a normal employee workstation should be interpreted differently from a request generated by a DNS server, web server, development system, or security appliance. Understanding the role of the source system helps establish what normal DNS behavior should look like.

Examine the Queried Domain

Next, examine the domain that was requested. Look at the complete domain rather than only the top-level domain. Check whether the domain belongs to a known business service, approved application, cloud provider, operating system service, or other expected destination.

Pay attention to unusual domain structures. Very long names, random-looking strings, excessive subdomains, or domains that appear unrelated to the organization's normal activity can be useful investigation clues. These characteristics are not proof of malicious behavior because legitimate services can also use complex domain structures.

Analyze Query Frequency

Frequency is one of the most useful indicators during DNS investigation. A single query may be completely normal, while hundreds or thousands of queries from one host within a short period may require additional investigation.

Look for repeated requests to the same domain, repeated requests to different subdomains, and regular intervals between queries. Consistent repeated activity can sometimes indicate automated software behavior rather than normal human browsing.

Look for Failed DNS Requests

Failed DNS responses can also provide useful information. A high number of NXDOMAIN responses means that the requested domain does not exist from the perspective of the DNS resolver.

Repeated failed lookups can have legitimate causes, such as incorrectly configured software or applications attempting several possible domains. However, a sudden increase in failed requests from one host, especially when combined with unusual domain structures, can justify deeper investigation.

Analyze the Time of the Activity

Establish when the suspicious DNS activity started and how long it continued. Determine whether it happened once, occurred for several minutes, or continued for hours or days.

Compare the activity with the normal schedule of the system. Unexpected activity outside normal operating periods can be useful context, but it should not be considered malicious by itself. Servers, automated jobs, backups, and scheduled applications can generate traffic at any time.

Compare With Historical Behavior

One of the strongest ways to identify suspicious DNS behavior is to compare the current activity with the host's previous behavior. Determine whether the system has contacted the domain before and whether the same pattern is common across other systems.

If hundreds of systems regularly query a domain, it may be part of a legitimate service. If only one workstation suddenly begins making unusual requests to the domain, the activity deserves more attention.

Check the DNS Response

Do not examine only the requested domain. Review the response returned by the DNS resolver when the information is available.

Determine whether the query returned an IP address, failed, or produced another response. If an IP address was returned, record it and investigate whether the same host later established a network connection to that address.

Correlate DNS With Network Logs

DNS activity should be correlated with firewall, proxy, HTTP, network connection, or other available network logs. This can help determine whether the DNS lookup was followed by actual communication.

For example, if a workstation resolves an unfamiliar domain and shortly afterward connects to the returned IP address over an unusual port, the two events should be investigated together.

Remember that a DNS query does not prove that a connection occurred. A system may perform a lookup without ever connecting to the returned address.

Correlate With Endpoint Activity

Endpoint logs can provide important information about which process or application generated the DNS request. Look for processes that started around the same time as the suspicious DNS activity.

Pay particular attention to unexpected scripts, command interpreters, PowerShell activity, recently created processes, unusual parent-child process relationships, downloaded files, or newly installed software.

If the DNS activity and suspicious process activity occur close together, the events should be treated as part of the same investigation rather than analyzed independently.

Check the User Context

Identify which user was logged into the source system when the activity occurred. The user's role and normal responsibilities can provide additional context.

For example, a developer's workstation may legitimately communicate with development platforms and package repositories that would be unusual on a finance workstation. Understanding the user and system context helps reduce false positives.

Possible Command and Control Indicators

Some compromised systems communicate with command and control infrastructure through DNS. Potential indicators include repeated queries to unusual domains, highly regular query intervals, large numbers of unique subdomains, and unusual domain structures.

Another clue can be a system that continuously performs DNS queries even when there is no obvious user activity. This can become more significant when endpoint logs reveal an unknown or suspicious process responsible for the activity.

None of these indicators should be treated as conclusive evidence on their own. A SOC Analyst should combine multiple observations before determining whether the activity is likely malicious.

Possible DNS Tunneling Indicators

DNS tunneling can abuse DNS requests to transfer information through DNS traffic. During an investigation, analysts may look for unusually long query names, encoded-looking strings, large numbers of unique subdomains, high query volumes, and repetitive communication patterns.

Legitimate applications can produce some of these characteristics, so the analyst should establish a baseline and correlate the DNS activity with endpoint and network evidence before making a determination.

Investigation Workflow

Start by identifying the suspicious DNS event and recording the timestamp, source IP, queried domain, query type, and response.

Next, identify the source host and determine whether the domain is expected for that system. Examine the frequency and duration of the activity, then compare it with historical DNS behavior.

After that, investigate the returned IP address and correlate the DNS event with firewall, proxy, HTTP, and network connection logs. Finally, examine endpoint activity and authentication information to determine which process and user may be associated with the event.

Example Investigation

A workstation begins making repeated DNS requests to an unfamiliar domain. The requests occur every few seconds and contain different, unusually long subdomains.

The analyst first identifies the workstation and confirms that the domain is not part of the organization's approved services. Historical logs show that the workstation had never contacted the domain before.

Network logs then show connections from the same workstation to the IP address returned by the DNS server. Endpoint logs reveal that an unusual script started shortly before the DNS activity began.

At this point, the DNS activity alone has not proven compromise. However, the combination of a new domain, repeated unusual queries, related outbound connections, and suspicious endpoint activity creates a much stronger reason for further incident investigation.

Normal vs Suspicious DNS Activity

Normal DNS activity usually matches the applications, users, and services expected on the system. It often occurs across many hosts and follows recognizable patterns.

Suspicious activity may involve a sudden behavioral change, unusual domains, abnormal frequency, repeated failures, strange subdomains, or communication that cannot be explained by the system's role.

The most important distinction is context. A behavior that is suspicious on one system may be completely normal on another system.

Common Investigation Mistakes

One common mistake is declaring a domain malicious simply because it is unfamiliar. Analysts should investigate the domain and its context before reaching a conclusion.

Another mistake is investigating the DNS server instead of the system that generated the request. The source host is often the most important starting point.

Analysts should also avoid looking at DNS in isolation. DNS becomes significantly more useful when correlated with endpoint, authentication, firewall, proxy, and network activity.

Finally, do not confuse DNS resolution with network communication. A successful DNS response only shows that the name was resolved; it does not prove that the host connected to the resulting IP address.

Questions and Answers

What is the first thing I should check during a suspicious DNS investigation?
Start with the source host. Identify the IP address or hostname that generated the query, then determine what type of system it is and whether the requested domain is expected for that system.

Is repeated DNS activity always malicious?
No. Applications, operating systems, monitoring tools, and cloud services can generate repeated DNS requests. The frequency becomes more important when it is unusual for the host and combined with other suspicious indicators.

Why should I investigate the returned IP address?
The returned IP can help determine whether the system later communicated with the destination. Correlating the DNS response with firewall or network connection logs can show whether the lookup was followed by actual network traffic.

What can unusual subdomains indicate?
Unusual subdomains can be generated by legitimate applications, but large numbers of random-looking or highly variable subdomains can also be associated with automated communication, command and control, or DNS tunneling. Additional evidence is required.

How can endpoint logs help with DNS investigation?
Endpoint logs may help identify the process, script, or application responsible for the activity. This can be especially useful when a suspicious DNS query occurs at the same time as an unexpected process or command execution.

When does suspicious DNS activity become more serious?
It becomes more significant when several indicators appear together, such as an unusual domain, abnormal query frequency, a new source host, related outbound connections, and suspicious endpoint activity. Multiple correlated indicators provide stronger evidence than a single DNS event.

Key Takeaway

Suspicious DNS Activity Investigation is about understanding the complete story behind unusual DNS behavior. Do not stop at the domain name. Identify the source host, examine the query pattern, check the response, compare the activity with historical behavior, and correlate it with network, endpoint, and authentication logs.

A good SOC Analyst does not ask only, “Is this domain suspicious?” The more useful question is, “Why did this system query this domain, what happened around the same time, and does the complete activity match the expected behavior of this host?”
