What Are DNS Logs?

DNS logs are records of Domain Name System activity. They show requests made by systems or applications when they need to translate a domain name into an IP address or perform another type of DNS lookup.

DNS is used constantly in modern networks. When a user opens a website, an application connects to an online service, or a system communicates with a remote server by hostname, DNS may be involved before the connection is established.

For a SOC analyst, DNS logs are valuable because they can reveal which systems are attempting to communicate with which domains. This can provide useful evidence during investigations, especially when looking for suspicious domains, unusual queries, malware activity, or command-and-control communication.

Why Are DNS Logs Important?

DNS activity can provide visibility into network behavior even when the analyst cannot directly see the full contents of the subsequent network connection.

A DNS log may show that a workstation requested a particular domain, when the request occurred, and what response was returned. This can help an analyst identify unusual destinations and build a timeline of network activity.

DNS logs can also be useful during incident response because malware frequently needs to resolve domains before communicating with remote infrastructure.

How Does DNS Work?

When a system needs to connect to a domain such as example.com, it may first send a DNS query asking for the IP address associated with that name.

The DNS resolver receives the request and attempts to provide the appropriate response. The client can then use the returned IP address to establish a connection with the destination.

In a typical environment, DNS requests may pass through an internal DNS server, security gateway, enterprise resolver, or another configured DNS service.

What Does a DNS Log Contain?

A DNS log can contain several useful fields depending on the DNS server, security product, or logging platform generating it.

Common information includes the timestamp, source IP address, queried domain name, query type, response code, returned IP address, and DNS server that processed the request.

Some environments may also record the hostname of the requesting system, user information, process information, or additional security metadata.

DNS Query Types

The query type describes the kind of DNS information being requested.

An A record query requests an IPv4 address. An AAAA query requests an IPv6 address. An MX query is associated with mail servers, while an NS query requests information about authoritative name servers.

A TXT query requests text records and can be used for legitimate purposes such as email security and domain verification. Because different query types have different purposes, the analyst should understand the expected use before deciding whether a query is suspicious.

DNS Response Codes

DNS responses can provide useful information about whether a query was successfully resolved.

A successful response indicates that the resolver was able to provide an answer. A response indicating that the domain does not exist can also be useful because repeated requests for nonexistent domains may reveal unusual software behavior or suspicious activity.

Response information should be interpreted together with the queried domain, source system, frequency, and timing.

Source IP Analysis

The source IP address identifies the system that generated the DNS request when that information is available.

Start by determining which host owns the address. Then consider whether that system should normally be making the observed DNS requests.

A workstation repeatedly requesting an unfamiliar domain may deserve investigation. However, the same domain request from a DNS server, proxy, security appliance, or known application server may have a completely different explanation.

Domain Analysis

The requested domain is one of the most important pieces of information in DNS analysis.

Determine whether the domain belongs to a known service, software provider, internal application, business partner, or another expected destination.

Pay attention to domains that are newly observed, unusually long, randomly generated, misspelled to resemble legitimate services, or unrelated to the normal purpose of the system making the request.

A suspicious-looking domain is not automatically malicious. Domains used by legitimate software can also have unfamiliar names, so additional evidence should be collected before making a conclusion.

Unusual Domain Names

Some suspicious domains may contain random-looking characters, unusual subdomains, excessive length, or patterns that do not resemble normal business services.

Attackers and malware may use automatically generated domains or frequently changing infrastructure. These patterns can make domain analysis useful for detecting suspicious network behavior.

The analyst should examine the domain as a whole and also consider how often it is queried and which systems are requesting it.

DNS Query Frequency

The frequency of DNS requests can reveal patterns that are not obvious from a single event.

A normal application may repeatedly query a small number of known domains. Malware may generate repeated requests to unusual domains, especially when attempting to communicate with remote infrastructure.

High query frequency does not automatically indicate malicious activity. Browsers, applications, monitoring systems, and other legitimate software can also generate many DNS requests.

Repeated Failed DNS Queries

Repeated requests for domains that do not resolve can be an important investigation clue.

One failed query may simply result from a mistyped domain or a temporary DNS problem. A system repeatedly generating requests for many nonexistent or unusual domains may require closer investigation.

Such behavior can sometimes be associated with malware, domain generation techniques, misconfigured applications, or other automated processes.

DNS and Malware Investigation

DNS logs can help identify systems that may be communicating with suspicious infrastructure. Malware may attempt to resolve a command-and-control domain, download server, or another attacker-controlled destination.

When a suspicious domain is identified, determine which internal systems requested it and when the requests occurred.

Then correlate the DNS events with process activity, network connections, authentication events, and file activity on the affected system.

DNS and Command-and-Control Activity

Some malware uses DNS as part of command-and-control communication. The infected system may repeatedly contact domains controlled by an attacker or use DNS queries to exchange information.

Unusual query frequency, strange subdomains, repeated requests to uncommon domains, and large amounts of changing query data can be useful indicators.

These characteristics are not proof of command-and-control activity by themselves. They should be correlated with endpoint and network evidence.

DNS Tunneling

DNS can also be abused to transport information through DNS queries and responses. This technique is commonly referred to as DNS tunneling.

During an investigation, unusually long or highly variable subdomains, large volumes of DNS queries, and unusual query patterns may deserve attention.

However, legitimate applications can also generate complex DNS traffic. Analysts should compare the activity with known applications and normal network behavior.

Internal vs External DNS Activity

Understanding whether a queried domain is internal or external can provide useful context.

Internal domains may belong to corporate systems, Active Directory infrastructure, internal applications, or private services. External domains may belong to websites, cloud services, software vendors, or other Internet destinations.

An internal system suddenly querying an unknown external domain may require additional investigation, particularly if the domain is unrelated to the system's normal function.

Normal DNS Activity

Normal DNS activity is usually associated with expected applications and services. Web browsers, operating system components, security tools, cloud applications, and business software can all generate DNS requests.

Normal traffic may include repeated requests to well-known services and internal domains used by the organization.

Understanding the baseline of a system is important because a domain that looks unusual in isolation may be completely normal for a particular application.

Potentially Suspicious DNS Activity

DNS activity may require additional investigation when a system repeatedly queries unfamiliar domains, generates unusually long or random-looking queries, contacts newly observed destinations, or produces large volumes of DNS requests without an obvious explanation.

Other useful indicators include requests immediately before suspicious outbound connections, domains associated with known malicious infrastructure, and DNS activity that begins shortly after suspicious process execution.

Correlating DNS With Other Logs

DNS logs become significantly more useful when correlated with other sources of evidence.

Process logs can help identify which application generated the activity. Authentication logs can show which account was active on the system. HTTP or network logs can show whether the system actually connected to the resolved destination.

File and endpoint logs can also reveal whether suspicious software appeared on the system around the same time.

Practical Example

Suppose a Windows workstation begins making repeated DNS requests to a domain that has never previously appeared in the environment. The requests occur every few minutes and contain unusual subdomains.

The analyst should identify the workstation, determine which process generated the DNS requests, and check whether the system established network connections to the resolved addresses.

If the activity began shortly after an unusual PowerShell process was executed and the workstation subsequently contacted the same external infrastructure, the DNS events may become an important part of the incident timeline.

DNS Investigation Workflow

Start by identifying the DNS query, timestamp, source system, queried domain, query type, and response.

Next, determine whether the domain is expected in the environment. Examine how frequently it is queried and whether other systems are making the same requests.

Then investigate the source system. Identify the user, running processes, recent authentication activity, and network connections around the same time.

Finally, correlate the DNS activity with other logs and build a timeline. Determine whether the behavior represents normal application activity, a configuration issue, or potentially malicious communication.

Common Mistakes

A common mistake is assuming that an unfamiliar domain is automatically malicious. Many legitimate applications use domains that analysts may not recognize immediately.

Another mistake is looking at domain names without identifying the source system. The same domain can be normal for one system and suspicious for another.

Analysts should also avoid treating DNS activity as proof of a successful network connection. A DNS query shows name-resolution activity, but additional network evidence may be needed to confirm what happened afterward.

Questions and Answers

What are DNS logs used for in a SOC?

DNS logs provide visibility into domain-resolution activity. They can help analysts identify which systems queried which domains and can provide useful clues about suspicious destinations, malware activity, and unusual network behavior.

What should I look for in a DNS log?

Focus on the timestamp, source IP, queried domain, query type, response, frequency, and relationship with other network or endpoint events. These fields help establish whether the DNS request fits normal behavior.

Is an unfamiliar domain automatically malicious?

No. Legitimate software frequently communicates with domains that may not be familiar to an analyst. The domain should be evaluated together with the source system, query frequency, application activity, and other evidence.

Why are repeated DNS queries important?

Repeated queries can reveal automated behavior. They may be generated by normal applications, but repeated requests to unusual domains or unusual subdomains can also be associated with malware or command-and-control activity.

What can unusual DNS subdomains indicate?

Unusual subdomains may be caused by legitimate applications, tracking systems, or content-delivery services. In some cases, however, long or constantly changing subdomains can be associated with DNS tunneling or other suspicious communication techniques.

Can DNS logs prove that malware connected to a server?

Not by themselves. A DNS query shows that a system attempted to resolve a domain. Network or endpoint logs should be checked to determine whether a connection was actually established and what happened afterward.

Why should DNS logs be correlated with process logs?

DNS logs can show which destination was requested, while process logs can help identify which application or process generated the activity. Correlating the two can connect network behavior to a specific process on the endpoint.

What is the most important skill in DNS analysis?

The ability to recognize abnormal patterns is more important than simply identifying strange domain names. Analysts should understand the source system, normal DNS behavior, query frequency, destination, and surrounding activity before deciding whether a DNS event is suspicious.

Key Takeaway

DNS logs provide a valuable view of network activity by showing which systems are requesting which domains. They can help SOC analysts identify unusual destinations, suspicious query patterns, malware-related communication, and potential command-and-control activity.

Effective DNS analysis requires context. Examine the source system, domain, query type, response, frequency, and timing, then correlate the DNS activity with process, authentication, HTTP, and other network logs. A single unusual DNS request may mean very little, but a repeated pattern connected to suspicious endpoint activity can become important evidence during an investigation.
