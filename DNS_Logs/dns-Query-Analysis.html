What is DNS Query Analysis?

DNS Query Analysis is the process of examining DNS requests made by systems, users, applications, and devices to understand what domains they are trying to resolve. A DNS query is normally generated when a system needs to translate a domain name such as example.com into an IP address.

For a SOC Analyst, DNS queries can provide an early view of network activity. Before a system connects to a remote server, it may first perform a DNS lookup. This makes DNS logs useful for identifying unusual domains, suspicious communication patterns, malware activity, command and control indicators, and potentially compromised systems.

Why is DNS Query Analysis Important?

DNS activity is generated by almost every connected system, which means a SOC environment can contain a very large number of DNS queries. Most of them are normal, such as requests for operating system services, software updates, cloud platforms, websites, and internal services.

The challenge is identifying the small number of queries that look different from normal behavior. A single unusual domain does not automatically indicate an attack. Analysts need to consider the domain, frequency, source system, time, query type, response, and other related network activity.

What Does a DNS Query Look Like?

A DNS log normally records information about the request and its response. The exact fields depend on the DNS server, resolver, network monitoring system, or SIEM collecting the data.

Important fields can include the timestamp, source IP address, queried domain, query type, response code, returned IP address, and DNS server or resolver. Some security products may also provide the hostname, username, process information, or other endpoint context.

Important DNS Query Types

A records are commonly used to resolve a domain name to an IPv4 address. For example, a system may request an A record for a web domain and receive an IPv4 address in the response.

AAAA records are used to resolve a domain to an IPv6 address. They are common in networks where IPv6 is enabled.

MX records identify mail servers responsible for receiving email for a domain. They are normally associated with email infrastructure.

NS records identify authoritative name servers for a domain. They are commonly used for DNS infrastructure and domain administration.

TXT records contain text information associated with a domain. They can be used for legitimate purposes such as email security and domain verification, but they can also appear in investigations involving unusual DNS activity.

What Should a SOC Analyst Look For?

The first thing to examine is the queried domain. Determine whether it is expected for the user, device, application, or environment. A domain that is unfamiliar to the organization deserves additional investigation, especially if it is associated with other suspicious activity.

Look at the structure of the domain as well. Very long domains, randomly generated-looking subdomains, unusual character patterns, or a large number of unique subdomains can be useful investigation clues. These characteristics are not proof of malicious activity because legitimate services can also generate complex domain names.

Frequency is another important factor. A system repeatedly querying the same unusual domain over a short period may be behaving differently from normal user activity. Repeated queries can become more significant when they continue at regular intervals.

Analysts should also examine failed DNS requests. A large number of NXDOMAIN responses may indicate that a system is repeatedly attempting to resolve domains that do not exist. This can happen for legitimate reasons, but unusual patterns may warrant investigation.

Source IP Analysis

The source IP identifies the system generating the DNS request. Instead of looking only at the domain, determine which device is making the request and whether that device is expected to communicate with the domain.

For example, if a workstation suddenly starts generating thousands of queries for unusual domains while other workstations do not show the same behavior, that host becomes more interesting from an investigation perspective.

After identifying the source system, check whether it belongs to a normal user workstation, server, security appliance, development system, or another type of device. The expected DNS behavior can be very different between these systems.

Time-Based Analysis

The timestamp helps establish when the DNS activity occurred. Compare the query time with the normal activity pattern of the system.

A workstation generating unusual DNS queries during normal working hours may have a different explanation from a workstation generating the same activity repeatedly during periods when the user is normally inactive.

Time correlation is especially useful when investigating a sequence of events. For example, DNS activity followed immediately by an outbound network connection and suspicious process activity provides more context than the DNS query alone.

Normal DNS Activity

Normal DNS activity usually includes requests for commonly used websites, operating system services, software repositories, cloud platforms, security services, internal applications, and other services required by the organization.

Normal traffic can still contain unfamiliar domains because applications frequently communicate with third-party services in the background. This is why analysts should avoid treating every unknown domain as malicious.

Suspicious DNS Activity

Potentially suspicious DNS behavior can include repeated requests to an unusual domain, a sudden increase in DNS activity, long or random-looking subdomains, large numbers of unique subdomains, repeated NXDOMAIN responses, or DNS requests from a system that normally generates very little DNS traffic.

Another useful clue is a change from the host's normal behavior. A workstation that normally contacts a predictable set of domains but suddenly begins querying several unrelated domains may deserve investigation.

DNS and Command and Control

Some malware uses DNS as part of command and control communication. In these situations, DNS queries may be used to locate infrastructure or exchange small amounts of information.

Possible indicators can include frequent queries, unusual subdomain patterns, high numbers of unique queries, or domains that do not match the normal software and business requirements of the host.

However, DNS activity by itself is not enough to confirm command and control. The analyst should correlate DNS logs with endpoint, firewall, proxy, HTTP, and other network telemetry before reaching a conclusion.

DNS Tunneling Indicators

DNS tunneling is a technique where DNS queries and responses are abused to transfer information through DNS traffic. Because DNS is normally allowed in many environments, attackers may attempt to hide communication inside DNS requests.

Potential indicators include unusually long query names, frequent requests, high numbers of unique subdomains, encoded-looking strings, and consistent communication patterns. These indicators require additional analysis because some legitimate applications also generate long or complex DNS names.

Correlation With Other Logs

DNS analysis becomes much more valuable when it is correlated with other security logs. If a suspicious DNS query is found, identify what happened before and after it.

Endpoint logs can show which process generated the activity. Network logs can show whether the system later connected to the resolved IP address. HTTP logs can reveal web requests to the destination. Authentication logs can show which user was active on the system at the time.

For example, a suspicious DNS query followed by a connection to the returned IP address and an unusual PowerShell process provides a stronger investigation path than the DNS query alone.

Example Analysis

Imagine a workstation generates a DNS query for a domain that is not normally seen in the environment. The domain contains a long and unusual subdomain, and the same workstation repeats the query every few seconds.

The analyst should first identify the source host and determine which user was logged in. Next, the analyst should check whether the domain is related to approved software or business activity. The returned IP address should then be compared with firewall or network connection logs.

If endpoint logs show that an unusual script or process started immediately before the DNS activity, the events should be investigated together. At this point, the DNS query is no longer an isolated event but part of a larger sequence that may indicate compromise.

Common Mistakes

One common mistake is treating every unfamiliar domain as malicious. Large organizations use many cloud services, content delivery networks, analytics platforms, software update systems, and third-party services that may not be familiar to every analyst.

Another mistake is focusing only on the domain name. The source system, frequency, timing, query type, response, and related network activity are equally important.

A third mistake is assuming that a DNS query proves that a connection occurred. DNS only shows that a lookup was performed. Additional network or endpoint evidence is needed to determine whether the system actually connected to the resulting IP address.

Questions and Answers

What is the main goal of DNS Query Analysis?
The goal is to understand DNS activity and identify queries that may be unusual, unauthorized, or related to suspicious behavior. Analysts compare DNS activity with the expected behavior of the host and organization.

Is an unknown domain automatically malicious?
No. An unknown domain can belong to a legitimate application, cloud provider, advertising service, software update mechanism, or other third-party service. It becomes more interesting when other indicators support the suspicion.

Why is the source IP important?
The source IP identifies the system generating the query. This allows the analyst to determine which host is responsible for the activity and compare its DNS behavior with its normal baseline.

Why are repeated DNS queries important?
Repeated queries can indicate normal application behavior, but they can also be an investigation clue when the destination is unusual or the frequency is abnormal. Regular repeated communication can be especially interesting when investigating possible malware or command and control activity.

Can DNS logs identify malware?
DNS logs can provide indicators associated with malware, but they normally cannot prove malware infection by themselves. Endpoint and network evidence should be correlated to determine what generated the DNS activity and what happened afterward.

What should I check after finding a suspicious DNS query?
Start with the source host, user, timestamp, domain, query type, response, frequency, and historical activity. Then correlate the event with endpoint processes, network connections, HTTP traffic, firewall logs, and authentication events.

Key Takeaway

DNS Query Analysis is an important SOC skill because DNS activity can reveal what systems are attempting to communicate with before or during a network connection. The most useful approach is not to judge a domain by its name alone, but to analyze the complete pattern: who made the query, what was requested, when it happened, how often it occurred, what response was returned, and what the system did afterward.
