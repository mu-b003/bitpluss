OpenID Connect (OIDC)

OpenID Connect (OIDC) is an authentication layer built on top of OAuth 2.0.

It allows applications to verify a user's identity and obtain basic profile information.

Why Use OIDC?

OAuth 2.0 answers:

What can the application access?

OIDC answers:

Who is the user?

OIDC is commonly used for Single Sign-On (SSO) and social logins.

Examples

• Sign in with Google

• Sign in with Microsoft

• Sign in with GitHub

• Enterprise SSO Solutions

Main Components

End User

The user who wants to authenticate.

Client

The application requesting authentication.

OpenID Provider (OP)

The identity provider that authenticates users.

Examples:

• Google

• Microsoft

• Okta

Relying Party (RP)

The application that trusts the OpenID Provider.

OIDC Authentication Flow

1- User clicks "Sign in with Google".

2- User is redirected to the OpenID Provider.

3- User authenticates.

4- The provider issues an Authorization Code.

5- The application exchanges the code for tokens.

6- The application verifies the user's identity.

OIDC Tokens

ID Token

The most important token in OIDC.

Contains information about the authenticated user.

Usually formatted as a JWT.

Example:

eyJhbGciOiJSUzI1NiIs...
Access Token

Used to access APIs and protected resources.

Refresh Token

Used to obtain new Access Tokens without requiring the user to log in again.

ID Token Claims

Claims are pieces of information about the user.

Common claims:

sub
name
email
picture
iat
exp

Example ID Token Payload

{
  "sub": "123456",
  "name": "John Doe",
  "email": "john@example.com",
  "exp": 1735689600
}

Scopes in OIDC

Scopes determine which user information can be accessed.

Common scopes:

openid
profile
email
address
phone

The "openid" scope is required for OIDC.

UserInfo Endpoint

Provides additional information about the authenticated user.

Example:

GET /userinfo

Response:

{
  "name": "John Doe",
  "email": "john@example.com"
}

OIDC vs OAuth 2.0

OAuth 2.0
---------
Authorization

OIDC
---------
Authentication + Identity

Common OIDC Security Issues

ID Token Validation Issues

The application does not properly validate the ID Token.

Missing Signature Verification

Accepting unsigned or forged tokens.

Token Replay

Reusing stolen tokens.

Weak Redirect URI Validation

Can lead to token theft.

Improper Audience Validation

Accepting tokens intended for another application.

Nonce Validation Missing

May allow replay attacks.

What Should a Penetration Tester Check?

• Is the ID Token signature verified?

• Is the issuer (iss) validated?

• Is the audience (aud) validated?

• Is the token expiration checked?

• Is nonce properly implemented?

• Is redirect_uri strictly validated?

• Can tokens be replayed?

• Are sensitive claims exposed?
