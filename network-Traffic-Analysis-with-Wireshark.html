Network Traffic Analysis with Wireshark

You can carry out this task practically in an isolated lab within a virtual machine if you do not have a lab you can set up your own using the provided link.

The command: This is sudo apt update then sudo apt upgrade -y used to update the package lists and then upgrade the system. The result: 105 packages available for upgrade, with "dpkg lock" messages appearing due to the unattended-upgrade process, and then the actual upgrade process begins.

Continued operation apt upgrade -y. Result: A breakdown of the packages to be upgraded and installed (84 upgrades, 9 new installations), with a total download size of 811 MB — preparing the system before the start of the practical exercise.

Commands: These are sudo apt install apache2 -ythen enable/start/status apache2 used to install, activate, run, and check the status of the Apache2 web server. Result: Apache2 is pre-installed (2.4.66-2ubuntu2.4), and the service has been successfully running for two days—ready to generate HTTP traffic later.

Commands: These are sudo apt install openssh-server -y then enable/start/status ssh used to install and activate the SSH service to allow remote connection. Result: openssh-server is pre-installed, the service is active (running), and it is listening on port 22.

The command: ip a is used to display network interface settings. The result: the ens33 interface has the address 192.168.81.129/24— the target address for subsequent network tests.

The command: sudo wireshark is used to open the network analysis program on an Ubuntu machine. The result: a welcome window appears with the ens33 interface selected as the capture interface.

The command (from Kali): ping 192.168.81.129 Used to generate ICMP traffic towards Ubuntu for capture. Result: Successful connection with a 0% packet loss rate across 39 packets.

Commands: These are ping -c 10 then curl http://192.168.81.129 used to generate an actual HTTP request to Apache. The result: Receiving the default Apache page in HTML format — confirmation that the web service is working.

Loop: for i in {1..5}; do curl http://192.168.81.129; done Used to generate multiple consecutive HTTP requests to increase traffic volume. Result: The Apache page is received 5 times.

Commands: nslookup bitpluss.comThese nslookup github.com are used to generate DNS queries. The result: Obtaining the IP addresses of the two domains via a DNS server 192.168.81.2— to later parse the DNS packets.

The command: wget http://192.168.81.129 Used to download the webpage as an additional means of generating HTTP traffic. Result: Successful download of a index.html.110.42K file.

Commands: ssh Mubarak@192.168.81.129 The `then` pwd, ` then` ls, exit is used to create an encrypted SSH session to generate detectable SSHv2 traffic. The result: successful login, execution of simple commands, and then session termination.

Display of the Wireshark window during actual capture on the ens33 interface. The result: Various packets appear (encrypted SSHv2, TCP FIN/ACK, NTP) between 192.168.81.128 and 192.168.81.129.

Menu: File > Save As in Wireshark. Used to start the process of saving the capture file (pcap).

The Save Capture File As window is used to specify the file name before changing the save location./home/soc-labnetwork-analysis.pcapng

The same window after changing the path to [the desired location /home/soc-lab/Desktop]. Result: The final file is saved network-analysis.pcapngto the desktop.

Menu: Statistics > Capture File Properties (selected). Used to access statistics for the saved capture file.

Capture File Properties window. Result: File size 280 kB, 1370 packets, capture time 00:10:58 , average 2.1 packets/second, 2,835 bits/second.

Menu: Statistics > Protocol Hierarchy (selected). Used to display the distribution of protocols in the captured motion.

Protocol Hierarchy Statistics window. The result: TCP accounts for 77.2% of the packets (SSH for 66.1% of them), IPv4 for 94.2%, along with DNS, HTTP, ICMP and ARP — accurately reflecting the types of traffic intentionally generated (SSH, HTTP, DNS, Ping) during the network analysis exercise.

Menu: Statistics > Endpoints, IPv4·18 tab. This is used to display a list of all IP addresses that participated in the connections and the amount of data sent and received for each.

The result: The two most active addresses are 192.168.81.128 (1,140 packets, 199 kB) and 192.168.81.129 (1,252 packets, 224 kB) — these are Kali and Ubuntu machines, along with several external addresses (Ubuntu NTP/connectivity servers, Cloudflare, etc.).

Menu: Statistics > Conversations (selected). Used to access details of bilateral conversations between devices.

Conversations window, IPv4·18 tab. The result: The largest conversation is between 192.168.81.128 and 192.168.81.129 with a size of 197 kB, 1,121 packets, and a duration of approximately 503 seconds — representing the main SSH/HTTP exchange between Kali and Ubuntu during the exercise.

Applying a filter icmpin the main capture window. The result: Displaying 98 packets (7.2% of the total) of Ping requests and responses (Echo request/reply) between 192.168.81.128 and 192.168.81.129 — confirming the success of the previously generated connectivity test.

Filter application http. Result: Display of 18 packets (1.3%) including GET requests and 200 OK/204 No Content responses between the two devices, plus a connection to an external address (91.189.91.98) — documenting HTTP traffic resulting from the previous curl/wget.

Filter application dns. Result: Displaying 16 packets (1.2%) including AAAA/A queries for domains such as connectivity-check.ubuntu.com, bitpluss.com, and github.com with responses containing matching IP addresses — documenting previous nslookup queries and automatic system updates.

Filter application tcp. Result: Display of 1,058 packets (77.2%) — Shows the TCP handshake process (SYN/SYN-ACK/ACK), retransmission attempts to the unavailable address 0.0.0.0.192, and then the flow of successful HTTP requests between 192.168.81.128 and 192.168.81.129.

Continued filter display tcpwith a focus on SSHv2 packets. The result: full documentation of the SSH protocol handshake (Protocol exchange, Key Exchange Init, PQ/T Hybrid Key Exchange, New Keys) and then the exchange of encrypted packets — reflecting the security of the SSH session resulting from the previous connection.

Filter application arp. Result: Displaying 58 packets (4.2%) showing ARP (Who has/is at) requests and responses between the MAC addresses of Kali, Ubuntu and Gateway machines — revealing the process of determining local network addresses (Layer 2) before any IP connection is initiated.
