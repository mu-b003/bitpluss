What is Suspicious HTTP Activity?

Suspicious HTTP activity is web traffic that does not match the expected behavior of a user, system, application, or web service. It can include unusual requests, abnormal request rates, unexpected HTTP methods, access to sensitive resources, repeated authentication attempts, suspicious parameters, or communication with an unfamiliar destination.

Suspicious HTTP activity does not automatically mean that an attack has occurred. The purpose of an investigation is to understand why the traffic occurred, identify the system responsible for it, determine what the server returned, and establish whether the activity is part of a larger security event.

Why Investigate Suspicious HTTP Activity?

HTTP traffic can expose important details about activity against web servers and applications. An investigation can help identify scanning, enumeration, unauthorized access attempts, exploitation attempts, suspicious downloads, compromised hosts, and unusual communication with external systems.

HTTP investigation is especially valuable when several events occur close together. A suspicious HTTP request followed by a successful response, a file download, and unexpected endpoint activity may indicate a much more important event than the individual request suggests.

Start With the Timestamp

Begin by recording the exact time of the suspicious HTTP request. The timestamp provides the starting point for building an investigation timeline.

Once the time is known, examine activity immediately before and after the event. Look for DNS queries, authentication events, process creation, network connections, additional HTTP requests, or other security events involving the same system.

Identify the Source

Determine which IP address or host generated the request. The source may be an internal workstation, server, proxy, NAT gateway, application, or external system depending on the logging environment.

If the source is an internal host, identify its hostname, system role, and associated user when possible. Understanding the system's purpose helps determine whether the HTTP behavior is expected.

If the source is external, examine whether it generated other requests against the same server or other systems. Repeated activity from the same source can provide additional context.

Identify the Destination

Determine which web server, domain, or application received the request. Establish whether the destination is internal or external and whether it is an approved service.

For external destinations, determine whether the system normally communicates with that service. A newly observed destination can be an investigation clue, especially when it appears together with unusual endpoint activity.

Examine the HTTP Method

Review the HTTP method used by the client. GET and POST requests are common in normal web traffic, but other methods may require additional context depending on the application.

Unexpected PUT or DELETE requests against sensitive resources can be significant because these methods may modify or remove application data. However, they can also be completely legitimate in APIs.

The important question is whether the method matches the normal functionality of the application.

Examine the Requested URL

Inspect the complete requested path and determine what the client was attempting to access. Look for sensitive directories, administrative interfaces, configuration resources, backup files, debug endpoints, login pages, and other resources that may not normally be accessed.

Compare the request with normal application behavior. A request to an administrative endpoint may be normal for an administrator but suspicious when generated by an ordinary user workstation or unknown external source.

Analyze Request Parameters

Review query parameters and other logged input associated with the request. Look for unusual values, unexpected lengths, encoded content, or input that does not match the application's normal use.

Some malicious requests may contain patterns associated with injection, traversal, or command execution attempts. However, analysts should avoid classifying a request based on a single string because legitimate applications can contain similar characters or encoded values.

Check the Response Code

Determine how the server responded to the suspicious request. A successful response can indicate that the requested resource was accessible, while a 401 or 403 may indicate that authentication or authorization prevented access.

Repeated 404 responses may indicate that a client is searching for resources that do not exist. Repeated 500 responses following unusual requests may also be important because they can indicate that the application encountered an error while processing the input.

The response code should always be interpreted in context. A 200 response does not mean that the request was legitimate, and a 404 response does not automatically mean that an attack occurred.

Analyze Request Frequency

Determine how often the source made the same or similar requests. A single unusual request may be accidental, while hundreds of requests within a short period may indicate automated activity.

Look for repeated requests to the same endpoint, requests to many different paths, and requests occurring at very regular intervals. These patterns can help distinguish human browsing from scripted activity.

Look for Scanning Behavior

Web scanning often produces a recognizable pattern. One source may request many different paths, files, directories, or parameters within a short period.

A large number of requests that return 404 responses can be an indicator of enumeration. Requests targeting administrative paths, configuration files, backup files, or other sensitive resources can provide additional context.

Before classifying the activity as malicious, check whether the source belongs to an approved vulnerability scanner, security team, monitoring platform, or other legitimate automated system.

Investigate Authentication Attempts

Login endpoints deserve particular attention. Multiple POST requests to an authentication endpoint can represent normal users attempting to log in, but a high number of attempts from one source can indicate automated credential attacks.

Check the number of failed attempts, targeted accounts, timing, source addresses, and whether a successful login occurred afterward.

If a successful authentication follows many failed attempts, correlate the event with account activity and endpoint logs. This can help determine whether valid credentials may have been obtained or abused.

Analyze the User-Agent

Examine the user-agent field when it is available. Normal browser traffic usually contains recognizable browser information, while scripts, scanners, command-line tools, and custom applications may use different values.

An unusual user agent becomes more useful when combined with high request frequency, multiple targeted paths, or other suspicious behavior.

User agents can also be modified or spoofed, so they should be treated as supporting evidence rather than proof of the identity or intent of the client.

Investigate Suspicious Downloads

Determine whether the suspicious HTTP activity resulted in a file or other content being downloaded. Identify the requested resource, response status, size when available, and source system.

If endpoint telemetry is available, determine whether the downloaded file was created, executed, or followed by another suspicious process. A download followed immediately by process creation can provide an important investigation lead.

Correlate With DNS Logs

Check DNS logs around the same timestamp. Determine whether the source system recently resolved the destination domain.

This can help establish the sequence of events. For example, a workstation may first resolve an unfamiliar domain, then establish HTTP communication with the returned address.

If the DNS domain is new for the host and the subsequent HTTP activity is unusual, the combined evidence may justify deeper investigation.

Correlate With Endpoint Activity

Endpoint logs can help answer an important question: which process generated the HTTP activity?

Look for newly created processes, scripts, PowerShell activity, command-line execution, downloaded files, persistence mechanisms, or other changes around the same time.

If an unexpected process starts immediately before the suspicious HTTP connection, investigate the process and its parent process. This can help connect network activity to a specific endpoint action.

Correlate With Authentication Logs

Authentication logs can help determine which account was active when the suspicious HTTP activity occurred. This is useful when investigating activity originating from internal systems.

Look for unusual logins, remote logons, repeated failed authentication attempts, or successful authentication following multiple failures. These events can provide additional context about whether the system or account may have been compromised.

Build an Investigation Timeline

A timeline helps transform individual log entries into a sequence of events. Start with the first relevant event and document the time, source, destination, action, and result.

For example, a timeline might show a DNS lookup, followed by an HTTP connection, followed by a suspicious request, a successful response, a file download, and then an unexpected process starting on the endpoint.

This sequence provides significantly more context than any single HTTP log entry.

Determine the Scope

After identifying suspicious activity, determine whether the behavior is isolated to one system or appears across multiple hosts.

Search for the same destination, URL, user agent, source pattern, or other relevant indicators in other HTTP logs. If multiple systems show the same unusual behavior, the incident may have a broader scope.

Scope analysis helps determine whether the event is an isolated false positive, a single compromised host, or part of a larger campaign.

Example Investigation

Imagine that an internal workstation begins sending a large number of HTTP requests to a web server. The requests target many different paths, and most of the responses are 404.

The analyst identifies the source workstation and confirms that it is not an approved vulnerability scanner. The requests occurred within a few minutes and used a user agent that is not normally observed from the workstation.

Further investigation shows that the workstation had recently resolved an unfamiliar domain. Endpoint logs also show that an unusual script started shortly before the HTTP activity.

The analyst now has several related indicators: unusual HTTP request volume, multiple targeted paths, an unexpected client, new DNS activity, and suspicious endpoint execution. These events should be investigated together to determine whether the workstation is compromised.

False Positives

Suspicious-looking HTTP traffic can have legitimate explanations. Security scanners, vulnerability assessments, monitoring systems, automated crawlers, APIs, application testing, and software services can all generate traffic that looks unusual.

Before escalating an event, verify whether the source is authorized to perform the observed activity. This is an important part of SOC analysis because unnecessary escalation creates noise and can hide more important incidents.

Common Investigation Mistakes

One common mistake is focusing only on the requested URL. The same URL can be legitimate for one user and suspicious for another depending on context.

Another mistake is treating a single suspicious request as proof of compromise. Strong investigations usually require multiple pieces of evidence and correlation.

Analysts should also avoid ignoring successful responses. A suspicious request that receives a successful response may be more important than a large number of unsuccessful requests because it may indicate that the requested resource was accessible.

Finally, do not forget to determine the scope. Finding one suspicious HTTP event should lead to a search for similar activity across the environment.

Questions and Answers

What should I check first when investigating suspicious HTTP activity?
Start with the timestamp, source IP, destination, HTTP method, requested URL, response code, and request frequency. These fields establish the basic context before deeper correlation.

Does a 404 response mean an attack occurred?
No. A 404 only means that the requested resource was not found. A large number of 404 responses from one source across many different paths can become an indicator of scanning or enumeration when the overall pattern is unusual.

Why is a successful HTTP response important?
A successful response can indicate that the requested resource was accessible. When the request itself is suspicious, a successful response may provide stronger evidence that the activity had an effect on the target.

How can I tell whether HTTP traffic is automated?
Look for high request frequency, very regular timing, many different URLs, unusual user agents, and behavior that would be difficult for a human user to generate manually. These indicators should be compared with known legitimate automation.

Why should I check DNS during an HTTP investigation?
DNS logs can show whether the system recently resolved the destination domain. Correlating DNS and HTTP activity can help establish the sequence between name resolution and subsequent web communication.

How can endpoint logs help?
Endpoint logs can identify the process or script associated with the network activity. This can help determine whether the HTTP traffic was generated by a normal browser or application, or by an unexpected process.

When should suspicious HTTP activity be escalated?
Escalation becomes more appropriate when multiple indicators support the suspicion, such as abnormal request patterns, unauthorized access attempts, suspicious endpoint activity, unusual destinations, successful access to sensitive resources, or evidence of compromise.

Key Takeaway

Investigating suspicious HTTP activity requires more than identifying an unusual URL or status code. A SOC Analyst should establish who generated the traffic, where it went, what was requested, how often it occurred, and how the server responded.

The investigation becomes stronger when HTTP data is correlated with DNS, endpoint, authentication, firewall, and other network logs. The objective is to turn individual web requests into a complete timeline and determine whether the activity is normal, suspicious, or evidence of a larger security incident.
