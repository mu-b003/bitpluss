What are Process Logs?

Process logs are records that provide information about programs and processes running on a system. They can help a SOC Analyst understand which application started, which user or account launched it, when it started, what command was executed, and sometimes which process started it.

Process activity is important because attackers usually need to execute something after gaining access to a system. They may launch command shells, scripting interpreters, download tools, execute malicious files, or use legitimate system utilities to perform their actions.

Process logs therefore provide valuable evidence about what happened on a host and can help connect an authentication event to the activity that followed.

Why are Process Logs Important for a SOC Analyst?

Authentication logs can tell you that a user logged into a system, but they usually do not tell you what the user did afterward. Process logs can provide that missing context.

For example, an unexpected SSH login followed by the execution of a shell, a download utility, and a scripting interpreter may indicate activity that deserves investigation. Process information can also help analysts identify suspicious behavior that does not generate an obvious authentication event.

Process logs are especially useful when investigating malware execution, command execution, privilege escalation, persistence, lateral movement, and suspicious administrative activity.

What is a Process?

A process is a running instance of a program. When an application or command is executed, the operating system creates a process to run it.

For example, opening a terminal creates a shell process. Running a command from that terminal creates another process. A web browser, text editor, system service, or security tool can also create one or more processes while running.

Understanding this parent-child relationship is important because processes do not always appear independently. One process often starts another.

What Information Can Process Logs Contain?

Process logs can contain several useful fields. Common fields include the process name, process ID, parent process ID, username, command line, executable path, timestamp, hostname, and process creation or termination information.

The exact fields depend on the operating system, logging configuration, security tools, and SIEM collection method.

Some environments may also record hashes, integrity information, file signatures, network connections, or additional endpoint telemetry associated with the process.

Process Name

The process name identifies the executable or program that is running. Examples include sshd, bash, python, powershell.exe, cmd.exe, or chrome.exe.

Process names provide useful context, but the name alone is not enough to determine whether a process is malicious. Attackers can use legitimate operating system programs to perform malicious actions.

For example, powershell.exe is a legitimate Windows program, but it can be used to execute malicious commands. Similarly, Linux utilities such as curl, wget, and bash can be used for completely legitimate administration or for malicious activity.

Process ID (PID)

A Process ID, or PID, is an identifier assigned to a running process by the operating system. It allows analysts and administrators to distinguish one process instance from another.

PIDs can be useful when following process activity across multiple log events. If several events reference the same PID, they may belong to the same process instance, depending on the operating system and logging source.

A PID should not normally be treated as a permanent identity because operating systems can reuse process IDs after a process terminates.

Parent Process

The parent process is the process that created or launched another process. This relationship is one of the most valuable pieces of information during process investigation.

For example, a terminal shell may start a command, or a service may start a worker process. These relationships can help an analyst understand how execution began.

An unexpected parent-child relationship can be a useful investigation clue. For example, a document application unexpectedly starting a command shell may deserve investigation, especially if the behavior is not normal for that environment.

Parent Process ID (PPID)

The Parent Process ID, or PPID, identifies the parent process associated with a process. By examining the PID and PPID together, an analyst can reconstruct part of the process tree.

Process trees are useful because they show relationships rather than isolated events. Instead of seeing only a suspicious executable, the analyst can determine which process launched it and what it launched afterward.

Command Line

The command line shows how a process was executed and can provide much more context than the process name alone.

For example, a log showing python tells you that Python was executed. A command line showing python script.py provides additional information about what was executed.

Command-line arguments may reveal files, URLs, scripts, parameters, encoded data, download locations, or administrative options. Because of this, command-line logging can be extremely valuable during investigations.

User and Account Context

The account associated with a process helps determine who or what launched it. The process may have been started by a normal user, administrator, root, a service account, or another system identity.

Unexpected execution under a privileged account can be more significant than the same process running under a normal user, although the surrounding context must always be considered.

Service accounts are also important because they may normally run specific applications but should not normally launch unrelated interactive tools or administrative commands.

Process Creation Time

The timestamp of process creation helps establish when execution occurred. Time is particularly useful when correlating process activity with authentication and other security events.

For example, an SSH login at 10:20 followed by a shell process at 10:21 and a suspicious command at 10:22 provides a useful sequence for investigation.

Accurate timestamps and consistent time zones are important when building timelines across different systems.

Normal Process Activity

Normal process activity depends on the system's purpose. A web server may regularly create web-server worker processes, while a database server may generate database-related processes.

Normal user activity may include browsers, terminals, editors, and office applications. System services may also create processes regularly as part of normal operation.

The key question is not whether a process is unfamiliar, but whether it makes sense in the context of the host, user, parent process, command line, and time.

Suspicious Process Activity

Suspicious process activity can include unexpected programs, unusual command lines, abnormal parent-child relationships, execution from unusual directories, processes running under unexpected accounts, or programs starting immediately after suspicious authentication.

Processes that download files, execute scripts, modify system settings, create accounts, or establish unexpected network connections may also deserve investigation.

A process should not be classified as malicious based only on its name. Attackers frequently use legitimate tools, while security products and administrators may also generate activity that initially appears unusual.

Living off the Land

Living off the Land refers to the use of legitimate tools already available on a system to perform actions that may be malicious.

Examples can include command shells, scripting interpreters, network utilities, file-management tools, and system administration utilities.

This behavior can make detection more difficult because the executable itself may be trusted. Analysts therefore need to examine the command line, parent process, account, destination, timing, and resulting activity instead of relying only on the executable name.

Process Trees

A process tree represents the relationship between processes. It can show which process started another process and help reconstruct an execution chain.

For example, a process chain could look like sshd → bash → sudo → python. This does not automatically indicate malicious activity. It simply shows a sequence that can be investigated.

A different process chain, such as an unexpected application launching a shell followed by a download utility, may deserve closer attention because the relationship may not match normal application behavior.

Process Path Analysis

The location of an executable can provide additional context. Legitimate system programs are normally installed in expected directories, while execution from temporary, user-writable, or unusual locations may require investigation.

However, unusual paths are not automatically malicious. Software installers, development environments, scripts, and legitimate applications can also run from non-standard directories.

The path should therefore be considered together with the file name, user, parent process, command line, and other available evidence.

Process and Network Activity

Processes become more interesting when they are associated with network connections. For example, a browser connecting to a website is expected, while an unusual command-line utility making an unexpected outbound connection may require investigation.

When network telemetry is available, correlate the process with the destination IP, domain, port, timestamp, and connection frequency.

This can help determine which process was responsible for an unusual network connection and whether the activity was expected.

Process and Privilege Activity

Privilege information is another important part of process analysis. A process running with elevated privileges may have access to sensitive files, system configuration, and administrative functions.

Investigate processes that unexpectedly transition from a normal user context to a privileged context. On Linux, this may involve sudo or other privilege mechanisms. On Windows, elevated process activity can be correlated with security events and account information.

Process Logs on Linux

Linux systems provide several sources that can help analysts understand process activity. System logs, audit logs, systemd journal entries, shell activity, and security tools can provide different levels of process information.

The Linux Audit framework can record process execution through events such as execve, depending on the configured audit rules. The systemd journal may also contain service and process-related information.

The available information depends heavily on the logging configuration. A system without process auditing enabled may not provide enough detail to reconstruct every command that was executed.

Process Logs on Windows

Windows provides process-related information through several security and endpoint logging mechanisms. Windows Security Event ID 4688 can record process creation when the appropriate auditing policy is enabled.

Process creation events can include information such as the new process, creator process, account, and command line when command-line auditing is configured.

Additional Windows telemetry, such as Sysmon, can provide richer process information including process relationships, executable paths, hashes, and other useful details depending on configuration.

Process Investigation Workflow

Start by identifying the process that requires investigation. Record its name, timestamp, account, PID, parent process, command line, and executable path when available.

Next, determine whether the process is expected on that host. Consider the system's role, the user account, normal administrative procedures, and the time of execution.

Then examine the parent process and process tree. Determine how the process started and what other processes it launched.

Finally, correlate the process with authentication, privilege, file, DNS, and network activity. This allows you to determine whether the process is an isolated event or part of a larger sequence.

Practical Example

Imagine a Linux server receives an unexpected SSH login from an unfamiliar source. Shortly afterward, a shell process starts under the logged-in account, followed by a command-line utility that downloads a file.

The analyst should connect these events into a timeline. The SSH authentication establishes access, the shell shows command execution, and the download process shows activity occurring after authentication.

The analyst should then determine what file was downloaded, where it was saved, whether it was executed, what network destination was contacted, and whether any privilege or persistence activity followed.

Common Mistakes

One common mistake is treating a process name as proof of malicious activity. Legitimate tools can be abused, and unfamiliar processes can be completely legitimate.

Another mistake is ignoring the parent process. A process can look suspicious by itself but become completely understandable when its parent and execution context are known.

Analysts should also avoid ignoring command-line arguments. The executable name may be normal while the arguments reveal a suspicious file, destination, or operation.

A final mistake is examining process activity without considering the host. What is unusual on a database server may be completely normal on a developer workstation.

Questions and Answers

What is the most important information in a process log?
The process name, command line, parent process, account, timestamp, and executable path are among the most useful fields. Together they provide context about what ran, how it started, who started it, and when it happened.

Is an unfamiliar process automatically malicious?
No. New software, administrative tools, updates, scripts, and legitimate applications can create unfamiliar processes. The process should be evaluated using its context and behavior.

Why is the parent process important?
The parent process shows how the process was launched. Unexpected parent-child relationships can reveal suspicious execution chains that would be difficult to identify by looking at process names alone.

Why is command-line information useful?
The command line can reveal arguments, scripts, files, URLs, parameters, and other information that explains what the process was actually doing. It often provides much more context than the executable name.

Can legitimate system tools be used in attacks?
Yes. Attackers often use legitimate operating system utilities because they are already installed and may not immediately appear malicious. This is why analysts should focus on behavior and context rather than simply whether a tool is legitimate.

How should process activity be correlated with SSH logs?
Start with the SSH authentication timestamp and account, then examine processes created around the same time. If the process account and timing match the SSH session, the events may form part of the same activity chain.

What makes a process more suspicious?
A process becomes more concerning when several indicators appear together, such as an unusual parent process, unexpected account, suspicious command line, unusual execution path, unexpected network connection, or execution shortly after suspicious authentication.

Key Takeaway

Process logs help a SOC Analyst understand what happened on a system after access was obtained. They provide visibility into programs, commands, users, parent-child relationships, and execution times.

The most effective process analysis does not focus on one field. Instead, analysts combine process name, command line, parent process, account, path, timing, and related network or authentication events to understand the complete activity.
