What is Process Activity Analysis?

Process Activity Analysis is the process of examining how programs execute and behave on a system. Instead of looking at a single process event, the analyst studies the process name, parent process, command line, user account, execution time, location, and related activity to understand what the process was doing.

For a SOC Analyst, process activity can provide important evidence about what happened on an endpoint. After an attacker gains access, they usually need to execute commands, launch programs, download files, modify the system, or perform other actions. These activities can leave process-related evidence.

The goal is not to treat every unusual process as malicious. The goal is to determine whether the process behavior makes sense for the host, user, application, and situation.

Why is Process Activity Analysis Important?

A security event often becomes meaningful when it is connected to process activity. An authentication event may show that an account logged in, but process activity can show what happened after the login.

For example, an unexpected SSH login followed by a shell, a download utility, and a scripting interpreter creates a sequence that deserves investigation. Similarly, a user opening an application may cause several normal child processes, while an unexpected application launching a command shell may require closer examination.

Process activity can help investigate malware execution, suspicious command execution, privilege escalation, persistence, lateral movement, and post-compromise behavior.

What Should You Analyze?

When investigating process activity, start with the basic process information. Identify the process name, process ID, parent process, parent process ID, user account, timestamp, command line, and executable path when available.

Then ask whether the process is expected on that system. Consider the role of the machine, the account that launched it, the time of execution, and the process that created it.

Finally, look at what the process did. Network connections, file operations, child processes, privilege changes, and other activity can provide additional context.

Process Name Analysis

The process name is a useful starting point but should never be the only factor used for detection. Many legitimate operating system tools can also be used during malicious activity.

Examples include bash, sh, python, curl, wget, and other administrative utilities on Linux. Windows provides similar examples such as cmd.exe, powershell.exe, and other built-in utilities.

The important question is why the process was executed, who executed it, what arguments were provided, and what process started it.

Command Line Analysis

Command-line information is one of the most valuable sources of process context. Two processes with the same executable name can perform completely different actions depending on their arguments.

For example, seeing python alone provides limited information. A command line containing python script.py provides additional context about the file being executed.

Command lines may also reveal URLs, file paths, scripts, parameters, encoded data, or administrative operations. Analysts should therefore examine the complete command line whenever it is available.

Parent-Child Process Analysis

Processes often create other processes, forming a parent-child relationship. Analyzing these relationships helps reconstruct how execution started and how it developed.

For example, an SSH service may create a user session, which starts a shell, which then launches another command. This can be normal administrative behavior.

An unusual application launching a command shell or scripting interpreter may be more interesting. The relationship does not automatically prove malicious activity, but it provides a reason to investigate the process chain.

Process Tree Analysis

A process tree displays processes as a hierarchy. It allows an analyst to follow the execution chain from the original process to its child processes.

A simple Linux example could look like sshd → bash → sudo → python. Each relationship should be interpreted according to the environment and the user involved.

Process trees are especially useful when investigating complex activity because they allow the analyst to see the complete execution path rather than isolated process events.

User Context

The account running a process is an important part of process analysis. Determine whether the process was started by a normal user, administrator, root account, service account, or another system identity.

A process that is normal for an administrator may be unusual for a standard user. Similarly, a service account launching an interactive shell may require investigation if that behavior is not expected.

Privileged processes deserve particular attention because they may have access to sensitive system resources.

Time-Based Analysis

Time helps analysts understand when process activity occurred and how it relates to other events.

Look for processes that appear immediately after authentication, processes that start during unusual hours, repeated execution at regular intervals, or multiple processes created within a short period.

Time becomes much more useful when it is correlated with other events. For example, a suspicious process created seconds after an unexpected login is more relevant than the same process appearing during a known maintenance operation.

Execution Path Analysis

The executable path can provide additional context about where a program was launched from. Legitimate operating system binaries are commonly stored in expected system directories.

Execution from temporary directories, user-writable locations, download folders, or unusual paths may require additional investigation.

However, an unusual path does not automatically mean that the file is malicious. Developers, installers, scripts, and legitimate applications may also execute from non-standard locations.

Normal Process Activity

Every system has a normal process baseline. A web server, database server, workstation, and security monitoring server will all generate different process activity.

Normal activity may include applications starting expected child processes, users opening browsers, system services creating worker processes, or administrators using command-line tools.

Understanding normal behavior is important because suspicious activity is often identified as a deviation from what normally happens on that host.

Suspicious Process Behavior

Suspicious process behavior can include unusual parent-child relationships, unexpected scripting activity, processes running under unexpected accounts, execution from unusual locations, suspicious command-line arguments, and processes starting immediately after an unusual authentication event.

Other warning signs include unexpected downloads, creation of additional processes, attempts to access sensitive files, privilege escalation, or unexpected outbound network connections.

None of these indicators should automatically be considered proof of compromise. Analysts should combine multiple pieces of evidence before reaching a conclusion.

Process Frequency and Repetition

The number of times a process executes can provide useful context. A process that normally runs once but suddenly executes hundreds of times may deserve investigation.

Repeated execution can have legitimate causes such as scheduled jobs, monitoring systems, application errors, or automated tasks. The analyst should therefore determine whether the frequency matches the expected behavior of the system.

Repeated execution combined with unusual command lines, external connections, or unexpected accounts becomes more significant.

Process and Network Connections

Network activity can help explain what a process was doing. If a suspicious process creates an outbound connection, investigate the destination, port, protocol, timing, and frequency.

For example, a browser connecting to an external website is normally expected. A command-line utility unexpectedly connecting to an unfamiliar external host may require more attention.

When possible, correlate process activity with DNS and network logs to determine which process contacted which destination.

Process and File Activity

Processes can create, modify, delete, or execute files. File activity can therefore provide additional evidence about process behavior.

An unexpected process creating executable files, modifying system configuration, or writing files into sensitive directories may require investigation.

The timing is important. If a suspicious process creates a file immediately after an unexpected login, the two events may be related and should be examined together.

Process and Privilege Escalation

Process activity can reveal attempts to obtain higher privileges. On Linux, this may involve commands executed through sudo or other privilege mechanisms.

An analyst should identify the account that started the process and determine whether the resulting process ran with elevated privileges.

Unexpected privileged execution is particularly important when it follows suspicious authentication or other abnormal activity.

Process Activity on Linux

Linux provides several ways to observe process activity. The ps command can display running processes, while tools such as top and htop provide a live view of running processes.

For security investigations, however, live process information may not be enough because a process may have already terminated. Audit logs, system logs, systemd journal data, endpoint monitoring tools, and other telemetry can provide historical evidence depending on the system configuration.

The Linux Audit framework can record process execution when appropriate audit rules are enabled. This can be especially useful for reconstructing command execution after an incident.

Process Activity on Windows

Windows process activity can be monitored through Windows Security auditing and endpoint telemetry. Security Event ID 4688 can record process creation when the required auditing configuration is enabled.

Additional telemetry such as Sysmon can provide more detailed process information, including process relationships, executable paths, command lines, and other fields depending on configuration.

When investigating Windows process activity, analysts commonly correlate process creation with authentication events, PowerShell activity, account changes, network connections, and other endpoint events.

Process Activity and Authentication

Authentication and process activity are often closely related. A user must normally have some form of execution context before performing actions on a system.

If an unusual login occurs and suspicious processes immediately appear under the same account, the events should be examined together.

This relationship can help distinguish an isolated process from activity that may be associated with a compromised account.

Process Activity Investigation Workflow

First, identify the process and collect its basic information. Record the process name, timestamp, account, PID, parent process, command line, and executable path.

Second, determine whether the process is expected for the host and account. Consider the role of the system and normal administrative activity.

Third, inspect the parent-child relationship and process tree. Determine how the process started and what it launched.

Fourth, investigate associated file, privilege, and network activity. Look for actions that occurred at approximately the same time.

Finally, correlate the activity with authentication and other security logs and build a timeline. The objective is to determine whether the process represents normal activity, an isolated anomaly, or part of a larger incident.

Practical Example

Imagine a Linux server normally runs web and database services. An analyst notices that a shell process was started by an unexpected user account at an unusual time.

The analyst examines the process tree and finds that the shell was created shortly after an SSH login from an unfamiliar source. The shell then launches a download utility, which connects to an external IP address.

The analyst should investigate the downloaded file, the destination address, the SSH authentication event, the account permissions, and any activity that occurred afterward.

The individual events may each have legitimate explanations, but their sequence creates a stronger reason for investigation.

Building a Process Timeline

A process timeline helps connect execution events into a sequence. Start with the earliest relevant event and record the processes that followed.

For example, an investigation might show an SSH login at 03:10, a shell process at 03:11, a download utility at 03:12, a new executable process at 03:13, and a privileged command at 03:14.

This sequence provides more investigative value than simply reporting that an unfamiliar process existed.

Common Mistakes

One common mistake is focusing only on the process name. A legitimate executable can be used for malicious purposes, and a strange-looking process can have a legitimate explanation.

Another mistake is ignoring the command line. Without command-line arguments, an analyst may miss important information about files, scripts, destinations, or actions.

Analysts should also avoid ignoring parent processes. The parent-child relationship often provides the context necessary to understand how execution started.

A final mistake is failing to establish what is normal for the host. Process activity must always be evaluated in the context of the system and its expected workload.

Questions and Answers

What is the difference between a process log and process activity analysis?
A process log is a record of an event involving a process. Process activity analysis examines those events together with their timing, parent processes, users, command lines, and related behavior to understand what actually happened.

Why is the command line important?
The executable name tells you what program ran, while the command line can show how it was used. Arguments may reveal scripts, files, URLs, parameters, or other actions that are important during an investigation.

Why should I analyze the parent process?
The parent process helps explain how the process was launched. An unexpected parent-child relationship can reveal suspicious execution that may not be obvious when examining the child process alone.

Is running a shell such as bash or PowerShell suspicious?
No. Shells are legitimate administrative tools. They become more interesting when they are launched by an unexpected process, account, or authentication session, or when their command line and subsequent behavior are unusual.

How can process activity help identify compromise?
Process activity can show what happened after access was obtained. When suspicious processes are correlated with authentication, privilege escalation, file changes, and network connections, they can provide evidence of post-compromise activity.

Does an unusual process path mean malware?
No. Software can legitimately run from temporary or non-standard locations. However, an unusual path combined with other indicators such as a suspicious command line or unexpected network connection should receive additional attention.

Why is process context more important than a single indicator?
Attackers can use legitimate tools, and legitimate systems can generate unusual-looking events. Looking at the complete context reduces false positives and helps the analyst distinguish genuine threats from normal administrative or application activity.

Key Takeaway

Process Activity Analysis is about understanding execution behavior rather than simply identifying running programs. A SOC Analyst should examine the process name, command line, parent process, user, path, timestamp, and related activity.

The most useful investigations connect process activity with authentication, privilege, file, DNS, and network events. By building a process tree and timeline, an analyst can move from an isolated event toward a clearer understanding of what happened on the system.
