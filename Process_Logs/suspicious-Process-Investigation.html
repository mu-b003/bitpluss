What is a Suspicious Process?

A suspicious process is a process whose execution, context, or behavior does not match what would normally be expected on a system. It may be an unfamiliar executable, a legitimate system tool being used in an unusual way, a process running under an unexpected account, or a process that creates an unusual chain of child processes.

A suspicious process is not automatically malicious. Security investigations must consider the system's purpose, the user, the parent process, the command line, the executable location, the time of execution, and related activity before determining whether the process represents a real security concern.

Why is Suspicious Process Investigation Important?

Processes are where many actions actually take place on an endpoint. After obtaining access, an attacker may execute commands, launch scripts, download files, modify configurations, create accounts, or attempt privilege escalation.

Investigating suspicious processes can therefore help identify activity that may not be obvious from authentication logs alone. It can also help connect an initial access event to the actions that followed.

For a SOC Analyst, the objective is to determine what started the process, who started it, what it executed, and what happened afterward.

Start With the Process Details

Begin by collecting the basic information available for the process. Important fields include the process name, process ID, parent process ID, parent process, username, timestamp, command line, executable path, and hostname.

If endpoint telemetry provides additional information such as file hashes, signatures, network connections, or file activity, collect those details as well.

Do not immediately classify the process as malicious. First establish the context around the event.

Analyze the Process Name

The process name is the first thing an analyst usually sees, but it should only be the starting point of the investigation.

Some processes are commonly used by attackers because they are already available on the operating system. Examples include bash, sh, python, curl, and wget on Linux, and cmd.exe, powershell.exe, and other built-in utilities on Windows.

The presence of one of these processes does not mean that the system is compromised. The analyst must determine how and why the process was executed.

Analyze the Command Line

The command line can reveal what the process was actually instructed to do. This makes it one of the most useful sources of evidence during process investigation.

Look for unusual arguments, scripts, file paths, URLs, downloads, encoded data, administrative commands, or operations that do not match the user's normal activity.

A legitimate program with an unusual command line can be more interesting than an unfamiliar program with a completely expected command line.

Analyze the Parent Process

Determine which process created the suspicious process. The parent process can provide important context about how execution began.

For example, a shell started by an administrator may be expected. A shell unexpectedly launched by a document viewer, web-facing application, or unrelated service may require deeper investigation.

Parent-child relationships should always be evaluated in the context of the operating system and application involved because legitimate software can also create unexpected-looking process chains.

Build the Process Tree

A process tree shows the sequence of process creation. It helps an analyst understand the execution chain instead of examining each process independently.

For example, a process tree might show sshd → bash → curl → downloaded-file. This sequence does not automatically prove malicious activity, but it provides a useful starting point for investigating what happened during the SSH session.

On Windows, a process tree might show an application launching a script interpreter and then another utility. The analyst should determine whether that execution chain is normal for the application.

Check the User Account

Identify the account associated with the process. Determine whether it is a normal user, administrator, root account, service account, or another system identity.

A process running under an account that normally does not perform administrative tasks may be more interesting if it suddenly launches privileged utilities.

Service accounts should also be reviewed carefully. They may legitimately run specific applications, but interactive shells or unrelated administrative commands under those accounts may require investigation.

Check the Execution Path

Examine where the executable was launched from. The path can help distinguish expected system software from files located in unusual directories.

Execution from temporary directories, user-writable locations, download folders, or other unexpected paths can be an investigation clue.

However, unusual paths are not proof of malicious activity. Legitimate software, development tools, installers, and scripts may also execute from these locations.

Analyze the Timestamp

Determine when the process was created and compare the time with other events.

Pay particular attention to processes that appear immediately after a suspicious authentication event, account change, privilege escalation, or file modification.

Time correlation can help determine whether multiple events are part of the same activity. A suspicious process occurring seconds after an unexpected login is more relevant than the same process occurring during a known maintenance operation.

Look for Suspicious Child Processes

After identifying the suspicious process, examine the processes it created. A process that launches several unexpected child processes may provide additional evidence about its behavior.

For example, a normal application launching its expected helper processes is usually not concerning. A process unexpectedly launching a shell, scripting interpreter, download utility, or administrative tool may require additional investigation.

Child-process behavior can sometimes reveal the actual purpose of the original process.

Investigate Network Activity

Determine whether the suspicious process created network connections. If network telemetry is available, identify the destination IP address, domain, port, protocol, timestamp, and frequency.

A process that unexpectedly communicates with an external host can be more concerning, especially when the destination is unfamiliar and the connection occurs immediately after suspicious execution.

However, many legitimate applications communicate with external services. The destination and purpose of the connection should be evaluated rather than assuming that every external connection is malicious.

Investigate DNS Activity

If the process connects to a domain name, correlate the activity with DNS logs when available. Determine when the domain was resolved and whether other hosts made similar requests.

DNS information can help connect a process to an external destination and provide additional context about the activity.

Unusual domains, repeated requests, or unexpected external destinations may increase the priority of an investigation, but they should be treated as indicators rather than automatic proof of malicious behavior.

Investigate File Activity

Check whether the suspicious process created, modified, deleted, or executed files. File activity can help explain what the process was doing.

For example, a process that downloads a file and then executes it should be investigated further. The analyst may need to identify the file, its location, how it was created, and whether other processes interacted with it.

Unexpected modifications to configuration files or sensitive directories can also provide important evidence.

Check for Privilege Escalation

Determine whether the suspicious process operated with elevated privileges or attempted to obtain them.

On Linux, this may involve sudo or other privilege mechanisms. On Windows, elevated process creation can be correlated with security events and account information.

A process that gains elevated privileges immediately after suspicious authentication should receive particular attention because it may indicate post-compromise activity.

Check for Persistence

Some suspicious processes may attempt to maintain access to the system. Look for account creation, SSH key changes, service creation, scheduled tasks, startup modifications, or other persistence-related changes depending on the operating system.

The process itself may not clearly reveal persistence, so correlation with account, service, file, and configuration logs is important.

Living off the Land

Attackers do not always need to introduce a clearly malicious executable. They can use legitimate operating system tools to perform malicious actions.

This behavior is commonly described as Living off the Land. Examples include using shells, scripting interpreters, download utilities, administrative tools, or other trusted programs.

Because the tools themselves may be legitimate, process investigation should focus on context and behavior. The command line, parent process, account, destination, timing, and resulting activity can provide the necessary evidence.

Compare With Normal Behavior

One of the most effective ways to investigate a suspicious process is to compare it with known normal activity.

Ask whether the process normally runs on this host, whether the user normally launches it, whether the parent process is expected, whether the command line is normal, and whether the execution time makes sense.

A process that is common across many systems may be normal, while the same process appearing under an unusual account with an unusual command line may deserve attention.

Correlate With Authentication Events

Authentication events can provide important context for process activity. If a suspicious process appears shortly after a successful SSH or Windows login, determine whether the process belongs to the same account and whether the timing suggests a relationship.

This can help establish a possible sequence such as initial access, process execution, privilege escalation, and subsequent network activity.

Correlate With Other Security Logs

A suspicious process should be investigated together with other available telemetry. Useful sources include authentication logs, privilege events, account changes, DNS logs, HTTP logs, firewall events, file activity, service logs, and endpoint security telemetry.

Correlation reduces the risk of making decisions from a single event and helps establish a complete timeline.

Practical Investigation Example

Imagine a Linux server where an unexpected account successfully authenticates through SSH from an unfamiliar external address. A short time later, a shell process is created under the same account.

The analyst examines the process tree and finds that the shell launches curl, which connects to an external address and downloads a file. A new executable process then appears.

The analyst should investigate the downloaded file, destination address, command line, file location, privilege activity, and any persistence changes that followed.

The individual events provide different pieces of evidence. When combined into one timeline, they can indicate whether the process activity is likely related to the suspicious SSH session.

How to Decide the Investigation Priority

Not every suspicious process requires the same response. Prioritize processes based on the number and strength of supporting indicators.

A single unfamiliar process with no unusual behavior may be low priority. A process with a suspicious command line, unexpected parent, privileged execution, external network connection, and relationship to a suspicious login should receive significantly more attention.

The goal is to combine indicators rather than relying on one simple rule.

Common Investigation Mistakes

One common mistake is assuming that a process is malicious because its name looks unfamiliar. New software and legitimate administrative tools can create unfamiliar process names.

Another mistake is trusting legitimate system utilities automatically. Attackers can abuse trusted tools, so the way the tool is used is often more important than the tool itself.

Analysts should also avoid ignoring the process tree. Looking only at the suspicious process can hide the event that actually initiated the execution.

Finally, avoid stopping the investigation after finding a suspicious process. Always look at what happened before and after it and determine whether related authentication, privilege, file, DNS, and network events exist.

Questions and Answers

What makes a process suspicious?
A process becomes more suspicious when its execution does not match the expected behavior of the host, user, or application. Unusual parent processes, command lines, accounts, paths, timing, or network activity can increase the level of concern.

Is an unknown executable enough to prove malware?
No. An unknown executable may belong to recently installed software, an internal tool, a script, or another legitimate application. Additional context such as its path, hash, parent process, command line, user, and behavior should be investigated.

Why is the parent process so important?
The parent process explains how the suspicious process was started. An unexpected process chain can reveal how execution occurred and may provide evidence of exploitation, script execution, or other suspicious behavior.

What should I check after finding a suspicious process?
Check the command line, parent and child processes, user account, executable path, timestamp, file activity, privilege changes, DNS requests, network connections, and related authentication events.

Can legitimate processes be used by attackers?
Yes. Attackers often use legitimate operating system utilities to execute commands, download files, modify systems, or perform other actions. This is why process behavior and context are important.

Why should I create a timeline?
A timeline shows how the activity developed. It can connect authentication, process execution, privilege escalation, file changes, and network connections into one sequence, making it easier to determine whether the events are related.

When should a suspicious process receive high priority?
Priority should increase when several indicators appear together, such as suspicious authentication, unusual process execution, unexpected privilege use, suspicious command-line arguments, file modifications, and external network communication.

Key Takeaway

Suspicious Process Investigation is not about identifying one strange executable and immediately declaring a compromise. It is about understanding the process in context.

A strong investigation examines the process name, command line, parent process, user, path, timing, child processes, network activity, file activity, and privilege context. These details should then be correlated with authentication and other security logs.

The most useful result is a clear timeline that explains how the process started, what it did, and whether its behavior is consistent with legitimate system activity or a possible security incident.
