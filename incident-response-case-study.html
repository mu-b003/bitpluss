Incident Response Case Study

This is a task you can carry out practically in your own isolated lab We will follow an attack scenario targeting an isolated virtual environment with the aim of generating logs and subsequently analyzing them.

'sudo apt update' The Command This command is used to update the list of available packages from system repositories without actually installing anything.The displayed results indicate that the system connected to the Ubuntu repositories, fetched the package lists, and found six packages that can be upgraded.

Command: `sudo apt upgrade -y` This command is used to install actual updates for upgradable packages; the `-y` option automatically answers "yes" to any prompts from the system. The results indicate that only two packages (`gnome-shell` and `gnome-shell-common`) were successfully upgraded, while four others remain un-upgraded due to the "phasing" mechanism (a gradual rollout of the update).

Command: `sudo systemctl enable ssh` This command is used to configure the SSH service to start automatically whenever the system boots. The resulting output indicates that the service has been successfully linked to systemd to ensure it starts automatically in the future.

Command: `sudo systemctl start ssh` This command is used to start the SSH service immediately in the current session. No messages appeared in the output, indicating that the service started without any issues.

Command: `sudo systemctl status ssh` This command is used to check the current status of the SSH service (whether it is running or stopped, and for how long).The output indicates that the service has been active (running) for 7 minutes and has successfully started listening on port 22 for both IPv4 and IPv6.

Command: `sudo adduser Omar` This command is used to create a new user named "Omar" on the system and automatically generate a dedicated home directory for him. The output indicates that the system warned the entered password was too short and weak (fewer than 8 characters); however, it allowed the process to proceed despite the warning, and the user "Omar" was successfully created after confirming the information by entering "y".

Command: `id Omar` This command is used to display the User ID (UID), Group ID (GID), and the groups to which the user "Omar" belongs. The results indicate that Omar has a UID of 1002 and a GID of 1002, and is a member of only two groups: his own group ("Omar") and the "users" group.

Command: `groups Omar` This command is used to display the names of the groups to which the user belongs in a direct and concise manner. The results indicate the following: Omar belongs only to the `Omar` and `users` groups; this means he is not part of the `sudo` group and does not possess administrative privileges.

Command: `sudo truncate -s 0 /var/log/auth.log` This command is used to completely clear the contents of the `auth.log` file and set its size to zero, without deleting the file itself.The results showed no error messages, meaning all previous logs in this file have effectively been erased.

Command: `sudo systemctl restart ssh`This command is used to restart the SSH service (stopping and then starting it).The results showed no issues, meaning the service was restarted successfully.

Command: `sudo systemctl status ssh`This command is used to verify that the service has resumed operation following the restart.The displayed results indicate that the service has been active (running) for just 17 seconds with a new process ID (PID 5716) and has resumed listening on port 22.

Command: nmap -sV 192.168.81.130 This command is used to scan a specific device on the network (in this case, 192.168.81.130) to identify open ports, services, and their versions.The results indicate that the target device is active and has two open ports: port 22 (SSH service running OpenSSH 10.2p1) and port 80 (Apache 2.4.66 web service), and that the operating system is Linux (Ubuntu).

Command: `touch passwords.txt`This command is used to create a new, empty text file named `passwords.txt`.There was no output, meaning the file was successfully created immediately.

Command: `nano passwords.txt` This command is used to open the file in the `nano` text editor for editing and entering content.The result is an empty editing screen ready for input.

There is nothing new here; this content was manually written inside the `passwords.txt` file. The content indicates that the attacker prepared a list of common, weak passwords (e.g., 123456, 123abc, abc123, password, admin) to use later in an attempt to guess the password for Omar's account.

Command: `hydra -l Omar -P passwords.txt ssh://192.168.81.130` This command is used to execute an automated brute-force attack against the SSH service by attempting to log in with the username "Omar" and testing each password listed in the `passwords.txt` file, one by one. The resulting output indicates that the tool successfully found the correct password for the "Omar" account, displaying the message "1 valid password found."

Command: ssh Omar@192.168.81.130 This command is used to actually connect to the target machine via the SSH protocol using the "Omar" account. The resulting output indicates that the login was successful using the discovered password and that access to the target machine (Ubuntu 26.04 LTS) was achieved.

Command: `whoami`Used to verify the identity of the current user in the session. Result: `Omar` — meaning the session is effectively under the name "Omar.

Command: hostname Used to identify the name of the currently connected machine. Result: it-team-VMware-Virtual-Platform — the name of the victim machine.

Command: pwd Used to determine the current path within the file system. Result: /home/Omar — meaning the user is inside their own home directory.

Command: `id` Used to display the current user's permission details. Result: The same as seen previously (uid=1002, and only two groups).

Command: `groups` Used to display the groups to which the current user belongs. Result: `Omar users` — confirming that the user does not belong to the `sudo` group.

Command: `sudo -l` Used to determine whether the current user can execute commands with sudo privileges. Result: Explicit denial — "Omar may not run sudo on this host," meaning the attacker has accessed the system using an account with limited privileges.

Command: `ls -la` Used to display all files (including hidden ones) within the current directory in detail. Result: Displays the contents of Omar's home directory—standard default system files (such as `.bashrc`, `.profile`, `.cache`, etc.)—with no additional, unusual files.

The command `cat /etc/passwd` is used to display a list of all users defined on the system. The output (continued in the next image) shows all default system accounts as well as actual user accounts.

This is a continuation of the previous command, without a new one. The significant results appearing at the end of the log indicate the presence of three actual users on the machine: it-team (the primary/administrator user), Noor, and Omar (the compromised account).

Command: `cat /etc/os-release` Used to view details about the installed operating system and its version. Result: The system is Ubuntu 26.04 LTS ("Resolute Raccoon").

Command: `uname -a` Used to display detailed information about the system kernel and architecture. Result: Linux kernel version 7.0.0-27-generic with x86_64 architecture.

Command: `last` It is typically used to display the system's recent login history. Result: The command is not installed on this machine; a message appeared indicating that it must be installed first (`apt install wtmpdb`).

Command: `history` This is used to display a list of all commands previously entered by the user during the current session. Result: It displays 13 previous commands executed by the attacker (the same commands explained in the previous images); this is crucial as it easily reveals all the attacker's steps to the investigator.

Command: `touch notes.txt` Used to create a new, empty file named `notes.txt`. Result: No output, meaning the file was created successfully.

The command: `echo "Incident Test" > notes.txt` It is used to write specific text directly into a file (overwriting any existing content). The result: No output appears on the screen, but the phrase is actually written into the file.

Command: `cat notes.txt` Used to display the file's content on the screen. Result: The phrase "Incident Test" appeared, indicating that the attacker was merely testing their ability to write to and read from the system.

Command: `cd /root` This is used to attempt to navigate to the directory belonging to the `root` user (the system's administrative root). Result: An explicit "Permission denied" error, indicating that the attacker lacks the necessary privileges to access this sensitive directory.

Command: `cat /etc/shadow` Used to attempt to read the file containing encrypted passwords for all system users (a highly sensitive file). Result: "Permission denied"—meaning the attempt failed because the file is protected and readable only by the root user.

Command: exit Used to terminate the current session and log out of the SSH connection. Result: The connection is successfully closed, returning control to the local terminal of the Kali machine.

Command: `grep "Failed password" /var/log/auth.log` This command is used to search the authentication log file for all lines containing the phrase "Failed password"—indicating failed login attempts. Result: Five failed login attempts were found; all involved the user "Omar" and originated from the same address (192.168.81.129), confirming a systematic brute-force attack against this account.

Command: grep "Failed password" /var/log/auth.log | wc -l This command is used to count the number of lines (i.e., the number of failed attempts) instead of displaying them all. Result: Exactly 5 failed attempts.

Command: `grep "Accepted password" /var/log/auth.log` This is used to search for all successful login attempts. Result: Two successful logins by user "Omar" from the same attacking address appeared, at two different times.

Command: grep "Accepted password" /var/log/auth.log | wc -l Used to count the number of successful logins. Result: 2 successful logins.

Command: `grep sshd /var/log/auth.log` This command is used to search the log specifically for lines related to the SSH service, allowing you to trace its entire activity from start to finish. The output tells the full story: an initial connection attempt that was interrupted, followed by five consecutive failed attempts by the user "Omar," a successful login, the system imposing a 20-second penalty delay on the attacker's address due to repeated failures (`srclimit_penalise`), a second successful login, and finally, a normal logout.

The command `grep "Omar" /var/log/auth.log` is used to search for all lines specifically mentioning the username "Omar," regardless of the event type. The result displays all details of this account's activity, including failed attempts, failed password checks (`unix_chkpwd`), the opening of two successful sessions (IDs 7 and 9), and their subsequent closures.

The command `grep "192.168.81.129" /var/log/auth.log` is used to search for all lines specifically associated with the attacker's IP address, regardless of the username. The result is the complete chronological sequence of the attack, filtered by this address, confirming that all suspicious events originated from a single source.

Command: `touch incident_evidence.log` Used to create a new, empty file to store incident evidence. Result: No output, indicating the file was created successfully.

The command `grep "192.168.81.129" /var/log/auth.log > incident_evidence.log` is used to save all logs associated with the attacker's address directly into an evidence file, rather than simply displaying them on the screen. The result: No output appears on the screen, but the data is actually saved within the file.

Command: `cat incident_evidence.log` This is used to verify the success of the save operation by displaying the file's contents.Result: The same log content appeared, confirming that the evidence file is now ready and contains all information related to this attack.

The command `grep "192.168.81.129" /var/log/auth.log | head -1` is used to display only the first line of the search results—that is, the first event recorded for this address. The result: The first event was a connection attempt that was interrupted.

The command `grep "192.168.81.129" /var/log/auth.log | tail -1` is used to display only the last line—that is, the most recent event recorded for this address. The result: The last event was user Omar disconnecting (a normal logout).

Command: grep "192.168.81.129" /var/log/auth.log Used to display all events in full, without filtering. Result: The same complete list as shown in the previous images.

Command: grep "Failed password" /var/log/auth.log (As before) Used to display failed login attempts. Result: The same 5 attempts for Omar.

Command: grep "Accepted password" /var/log/auth.log (As before) Used to display successful login attempts. Result: The same two successful logins for Omar.

Command: `grep "session closed" /var/log/auth.log` This is used to display all instances of session closures on the system for any user. Result: Closed sessions appeared for several users (root via sudo and CRON, Omar, gdm-greeter), indicating that this encompasses general system activity, not just the attacker's activity.

The command `grep "session opened" /var/log/auth.log` is used to display all instances of sessions being opened on the system. The result showed open sessions for `root`, `Omar` (twice), `gdm-greeter`, and `it-team`, providing a comprehensive overview of everyone who logged into the system during that period.

Command: `last` Used to display the system login history (presumably since the system was installed). Result: Several local sessions for `it-team` (tty2) appeared, along with a single session for user `Omar` via the network (pts/1) from address 192.168.81.129 at 19:45; this session was still active ("still logged in") at the time the screenshot was taken.

Command: `last Omar` Used to filter the previous result and display sessions for the user "Omar" only. Result: Confirms the single session for "Omar" originating from the attacking address.

Command: `grep -oP '(?<=from )(\d{1,3}\.){3}\d{1,3}' /var/log/auth.log | sort -u` This is used to extract all unique IP addresses appearing after the word "from" in the log (i.e., all sources that attempted to connect), while removing duplicates. The result is a single address: 192.168.81.129, meaning all suspicious activity originated from just one source.

The command `grep "Failed password" /var/log/auth.log | awk '{for(i=1;i<=NF;i++) if($i=="from") print $(i+1)}' | sort | uniq -c | sort -nr` is used to count the occurrences of each IP address specifically in failed attempts and to sort them in descending order by frequency. The result is `5 192.168.81.129`, meaning this address alone is responsible for all five failed attempts.

The command `grep "Failed password" /var/log/auth.log | awk '{print $(NF-5)}' | sort | uniq` is used to specifically extract the username targeted by the failed attempts. The result is just "Omar"—meaning the attack targeted one specific account.

The command `grep sudo /var/log/auth.log` is used to display all instances of `sudo` usage on the system, revealing who executed administrative commands and when. The results showed that the user `it-team` used `sudo` to perform tasks such as restarting SSH, checking its status, and installing the `wtmpdb` tool—representing legitimate administrative activity by the technical team, rather than the attacker.

Command: `grep "authentication failure" /var/log/auth.log` This is used to search for all instances of authentication failure (in a format different from "Failed password"). Result: The same 5 authentication failures for user "Omar" from address 192.168.81.129; this confirms—from another part of the log—the same number of failed attempts.

Command: `grep -Ei "adduser|useradd|new user" /var/log/syslog` This command is used to search the system log (`syslog`) for any new user creation events on the machine, using multiple keywords. Result: It clearly shows that the user "Omar" was created using the `adduser` tool, detailing the entire process—UID/GID selection, creation of a private group, creation of the home directory (`/home/Omar`), copying of default configuration files from `/etc/skel`, and addition to the `users` group. This accurately documents the date and time the account—which was subsequently targeted in the attack—was created.
