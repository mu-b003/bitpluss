Unauthorized User Investigation

Command: `sudo apt update` This command is used to update the list of available packages from system repositories without actually installing anything. The output indicates that the system found 204 packages eligible for upgrade. Command: `sudo apt install openssh-server -y` This command is used to install the SSH server on the machine, enabling remote connections to it. he o tput indicates that the installation was successful; `openssh-client` was upgraded, and `openssh-server` was installed along with its dependencies.

Command: `sudo systemctl restart ssh` This command is used to restart the SSH service after installation, ensuring it activates with the new settings. The output showed no error messages, indicating the service restarted smoothly.Command: `sudo systemctl status ssh` This command is used to check the status of the SSH service after the restart. The output indicates that the service has been "active (running)" for just 31 seconds and is actively listening on port 22 (IPv4 and IPv6), even though its "preset" status is "disabled."

Command: `sudo adduser Omar` This command is used to create a new user named "Omar" on the system. The output indicates that the system warned that the password was too short (fewer than 8 characters) but allowed the process to proceed; the user "Omar" was successfully created after the information was confirmed. Command: `cut -d: -f1 /etc/passwd` This command is used to extract only the first column (usernames) from the `/etc/passwd` file. The output displays a list of all usernames defined on the system (the beginning of the list shows default system accounts).

This continues the output of the command `cut -d: -f1 /etc/passwd` from u3 (the list extends further down). The significant result appearing at the end of the output indicates the presence of the username "Omar" among the system users—which is expected, given that it was just created. However, its presence here confirms that the investigation should proceed from the premise that this account is the focus of suspicion.

Command: `sudo usermod -aG sudo Omar` This command is used to add the user "Omar" to the `sudo` group, thereby granting him full administrative privileges on the system. No error messages appeared, indicating the operation was successful; Omar now possesses root privileges via `sudo`. This is a highly sensitive step from a security perspective, as it paved the way for Omar to later create the hidden "door" account.

Command: `sudo truncate -s 0 /var/log/auth.log` This command is used to completely empty the contents of the authentication log file (`auth.log`) and reduce its size to zero, without deleting the file itself. The results showed no error messages, meaning all previous logs in the file were effectively erased—a highly concerning indicator, as it implies that someone (with administrative privileges) attempted to cover their tracks by wiping the login logs.

Command: `ip a` This command is used to display details of the device's network interfaces and their associated IP addresses. The results indicate that the device has a network interface named `ens33` with the local IP address `192.168.81.129`, which is the address of the victim machine itself.

In this step, we will execute an attack aimed at generating logs.

(From the attacker's Kali machine) Command: ssh Omar@192.168.81.129 This command is used to connect to the victim machine via SSH using the "Omar" account. The resulting output indicates that the login was successful and the user has effectively accessed the machine.

Command: `sudo -l` This command is used to list the commands the current user can execute with `sudo` privileges. The output indicates that Omar possesses full privileges: `(ALL : ALL) ALL`. Command: `sudo useradd -m door` This command is used to create a new user named "door" and generate a home directory for them. The out ut s owed no errors, meaning the account was successfully created—a highly critical indicator: Omar has created a hidden account to serve as a backdoor. Command: `sudo passwd door` This command is used to set a password for the new "door" account. The output issued a warning about a weak password, but the password was successfully set despite the warning.

Command: `sudo usermod -aG sudo door` This command is used to add the "door" account to the `sudo` group, thereby granting it full administrative privileges. The output showed no errors, indicating the operation succeeded; there are now two accounts with administrative privileges: Omar and door. Command: `id door` Result: `uid=1002(door) gid=1002(door) groups=1002(door),27(sudo)` — confirming that "door" is a member of the `sudo` group. Command: `su - door` Used to switch to the "door" account directly from Omar's session. The output indicates a successful switch, and the attacker began exploring the machine from within this new account. Command: `sudo -l` (from within the "door" account) The output shows an initial failed authentication attempt followed by success, revealing that "door" also possesses `(ALL : ALL) ALL` privileges. Command: `ls -la` Result: Only standard default system files; no additional suspicious tools. Command: `cat /etc/passwd` Result (to be continued): The beginning of the user list display.

Continuing from the output of the `cat /etc/passwd` command on u9, the significant results at the end of the log indicate the presence of three human accounts: `soc-lab` (the legitimate user), `Omar` (the account initially compromised), and `door`—the hidden account created by the attacker as a backdoor.

Command: `touch mypasswords.txt` Result: No output, meaning the file was created successfully. Command: `echo "1111,2222,3333,abc" > mypasswords.txt` Used to write a list of weak, sample passwords directly into the file. Result: No output on the screen, but the data was written into the file. Command: `exit` (twice) The resulting output indicates exiting the `door` account first, followed by fully terminating the SSH connection.

The command: `cut -d: -f1 /etc/passwd` The result: The list of users is displayed again (the SOC-Lab investigation team repeats the same check to verify).

This follows the result of the previous command. The significant results at the end of the list confirm the existence of three human accounts—soc-lab, Omar, and **door**—providing the investigator with official proof of two suspicious accounts.

Command: `id door` Result: `uid=1002(door) gid=1002(door) groups=1002(door),27(sudo)` — confirming the `door` account's privileges.Command: `groups door` Result: `door : door sudo` — further confirmation that this account possesses full administrative privileges.

The command `sudo journalctl | grep -Ei "useradd|adduser"` is used to search the comprehensive system logs for any new user creation processes. The results tell the story chronologically: at 20:45, `soc-lab` created the "Omar" account. Later, at 21:06, Omar himself (via a remote SSH session) executed `useradd -m door`—conclusive evidence that Omar was the one who created the backdoor.

Command: `sudo journalctl | grep "door"` The resulting output summarizes the lifecycle of the `door` account: creation by Omar, password assignment, addition to the `sudo` group twice, a login via `su` from Omar to `door`, a failed authentication attempt, and finally, the closing of the session.

Command: `sudo journalctl | grep "passwd"` The results indicate: a password change for `soc-lab` (17:28), a password change for `Omar` (20:45), and the most significant event—a password change for `door` at 21:06:42, which temporally aligns with the account creation.

The command: `sudo journalctl | grep "usermod"` The results reveal two significant events: the first (21:02:27), where `soc-lab` itself granted `Omar` sudo privileges; and the second (21:08:53), where `Omar` granted `door` the same privileges—demonstrating that `Omar` exploited his privileges to expand the breach.

The command is: `sudo journalctl | grep "COMMAND="` The resulting output provides a comprehensive chronological overview: system updates and SSH installation (by `soc-lab`), the creation of the `Omar` account, granting it `sudo` privileges, and then—from within the `Omar` account—the creation of the `door` account, the setting of its password, and the granting of `sudo` privileges to it. Subsequently, `soc-lab` initiates the investigation process (using commands such as `grep Failed password`, `tail`, `head`, `cat`, `journalctl -u ssh`, and `grep Accepted password`).

Same thing: `sudo journalctl | grep "door"` (repeated later for confirmation). The results match what appeared in u16—final confirmation of the sequence of events.

The command `sudo journalctl | grep -E "su:|session opened|door"` is used to comprehensively search for all session openings and any mention of the word "door." The resulting output provides a complete picture: standard login sessions for `gdm-greeter`, `soc-lab`, and `root`; an SSH session opened for "Omar"; the creation of the "door" user, the setting of their password, and the granting of `sudo` privileges; followed by an `su` session from "Omar" to "door" and its subsequent closure.

This is a continuation of the previous result. The observed results indicate a return to normal activity following the closure of the 'door' session—specifically, repeated logins for 'gdm-greeter', 'soc-lab', and 'root', with no further sign of the 'Omar' or 'door' accounts thereafter.

Command: `id door` Used to re-verify the privileges of the `door` account as a final authentication step. Result: `uid=1002(door) gid=1002(door) groups=1002(door),27(sudo)` — a final confirmation that this suspicious account still exists and retains full `sudo` privileges, necessitating its immediate deactivation as a remedial measure.
