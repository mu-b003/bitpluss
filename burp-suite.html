Introduction — What is Burp Suite?

Burp Suite is the most widely used web application security testing platform in the world. Developed by PortSwigger, it acts as a proxy between your browser and the target web application — letting you intercept, inspect, modify, and replay every HTTP/HTTPS request and response.

What Can Burp Suite Do?

Intercept and modify HTTP/HTTPS requests — Discover hidden content — Fuzz parameters for vulnerabilities — Automate attacks — Scan for OWASP Top 10 vulnerabilities — Replay and manipulate requests — Brute force login forms — Decode and encode data.

Editions

Community Edition  — Free — Core tools available (Proxy, Repeater,
                    Decoder, Comparer, Sequencer)
                    No automated scanner — manual testing only

Professional       — Paid — Full active scanner, Collaborator,
                    advanced Intruder, all extensions

Enterprise         — For large organizations — automated CI/CD scanning

Installation

# Download from https://portswigger.net/burp/releases

# Linux
chmod +x burpsuite_community_linux_*.sh
./burpsuite_community_linux_*.sh

# Windows / macOS
Run the installer — follow the wizard

# Kali Linux (pre-installed)
burpsuite

Requirements

Basic understanding of HTTP (requests, responses, headers, cookies). Only test applications you own or have explicit written permission to test — unauthorized testing is illegal.

Setting Up Burp Suite

First Launch

On startup, Burp asks you to create or open a project. Community Edition only supports temporary projects — Professional saves full project state to disk.

1. Open Burp Suite
2. Select "Temporary project" → Next
3. Select "Use Burp defaults" → Start Burp

Configuring the Proxy Listener

Burp's proxy listens on localhost port 8080 by default. Your browser must be configured to send traffic through this proxy.

Verify in: Proxy → Options → Proxy Listeners
Default:   127.0.0.1:8080

Configuring Your Browser

The easiest method is using the built-in Chromium browser:

Proxy → Open Browser
This launches a pre-configured Chromium with Burp proxy and CA
certificate already set up — no manual configuration needed.

To configure Firefox manually:

1. Firefox → Settings → Network Settings → Manual proxy
2. HTTP Proxy: 127.0.0.1   Port: 8080
3. Check "Also use this proxy for HTTPS"
4. Click OK

Installing the CA Certificate (HTTPS)

To intercept HTTPS traffic, you must install Burp's CA certificate in your browser. Without it, HTTPS sites show SSL errors.

1. With proxy configured, visit: http://burpsuite
   — or — http://127.0.0.1:8080
2. Click "CA Certificate" — download cacert.der
3. Firefox: Settings → Privacy → View Certificates →
            Authorities → Import → select cacert.der
            → check "Trust for websites" → OK
4. Chrome:  Settings → Privacy → Manage Certificates →
            Authorities → Import → select cacert.der

FoxyProxy — Easier Browser Switching

FoxyProxy is a browser extension that lets you toggle Burp proxy on/off with one click — highly recommended.

1. Install FoxyProxy extension in Firefox or Chrome
2. Add a new proxy: 127.0.0.1:8080
3. Toggle it on when testing, off for normal browsing

Scope Configuration

Setting a scope limits Burp to only process traffic for your target — prevents capturing irrelevant requests from other tabs.

Target → Scope → Add
Enter the target URL: https://target.com
Check "Use advanced scope control" for fine-grained control

In Proxy → Options → enable:
"And URL is in target scope" under Intercept options
Proxy — Intercepting Requests

What is the Proxy?

The Proxy is Burp's core tool. It sits between your browser and the web server — every request your browser sends passes through Burp first, giving you the opportunity to read, modify, or drop it before it reaches the server.

Intercept Tab

Proxy → Intercept

Intercept is on  — Every request is paused and shown to you
                   You must click Forward or Drop for each one

Intercept is off — Requests pass through silently (still logged
                   in HTTP History)

Buttons:
Forward   — Send the request as-is (or modified)
Drop      — Discard the request — browser gets no response
Action    — Send to Repeater, Intruder, Scanner, etc.

Reading a Captured Request

POST /login HTTP/1.1
Host: target.com
Content-Type: application/x-www-form-urlencoded
Cookie: session=abc123
Content-Length: 34

username=admin&password=hunter2

Every part of this is editable — change the username, modify the cookie, add headers — then click Forward to send your modified version.

HTTP History

Proxy → HTTP History

Every request that passed through the proxy is logged here —
even when Intercept is off. Columns include:
— Method (GET/POST/PUT...)
— URL
— Status code
— Response length
— MIME type
— Time

Right-click any request → Send to Repeater / Intruder / Scanner

Intercepting Responses

By default Burp only intercepts requests. To also intercept and modify server responses:

Proxy → Options → Intercept Responses
Check: "Intercept responses based on the following rules"
Enable: "Or: Content type header matches text"

Useful for:
— Removing JavaScript validation
— Changing response status codes (403 → 200)
— Modifying hidden field values in HTML forms

Match and Replace

Automatically modify requests or responses matching a pattern — without manually intercepting each one.

Proxy → Options → Match and Replace → Add

Example — Remove security header from every response:
Type:    Response header
Match:   X-Frame-Options: DENY
Replace: (leave empty)

Example — Change User-Agent automatically:
Type:    Request header
Match:   User-Agent: .*
Replace: User-Agent: Googlebot/2.1
Repeater — Manual Request Manipulation

What is Repeater?

Repeater lets you send a single HTTP request as many times as you want — modifying it each time and immediately seeing the server's response. It is the tool you will use most for manual vulnerability testing.

Sending a Request to Repeater

From Proxy → HTTP History: right-click any request → Send to Repeater
From Intercept: click Action → Send to Repeater
Keyboard shortcut: Ctrl+R

The Repeater Interface

Left panel  — The HTTP request (fully editable)
Right panel — The server's response

Buttons:
Send      — Send the current request
Cancel    — Abort a pending request
< >       — Navigate through request history (undo/redo)

What to Do in Repeater

Testing SQL Injection:
  Original:  id=1
  Test:      id=1'
             id=1 OR 1=1--
             id=1 UNION SELECT null,null--

Testing XSS:
  Original:  search=hello
  Test:      search=<script>alert(1)</script>
             search=<img src=x onerror=alert(1)>

Testing IDOR (Insecure Direct Object Reference):
  Original:  /api/user/profile?id=1001
  Test:      /api/user/profile?id=1002
             /api/user/profile?id=1000

Testing Authentication Bypass:
  Remove the Cookie header entirely — does it still work?
  Change role=user to role=admin in the request body

Testing Path Traversal:
  Original:  /download?file=report.pdf
  Test:      /download?file=../../../etc/passwd
             /download?file=....//....//etc/passwd

Inspector Panel

The Inspector on the right side of Repeater (and Proxy) breaks down the request into sections for easy editing — no need to manually edit raw text.

Request Attributes  — Method, URL, HTTP version
Query Parameters    — URL parameters (?key=value)
Body Parameters     — POST body parameters
Request Headers     — All headers with edit/add/delete
Cookies             — Parsed cookie values
Intruder — Automated Attacks

What is Intruder?

Intruder automates sending a request many times with different payload values inserted at positions you define. Used for brute forcing, fuzzing, parameter enumeration, and credential stuffing.

Note: In Community Edition, Intruder is rate-limited (slow). For fast attacks use the Professional edition or external tools like ffuf or hydra.

Sending to Intruder

Right-click any request → Send to Intruder
Keyboard shortcut: Ctrl+I

Step 1 — Positions Tab

Define where in the request payloads will be inserted. Burp auto-detects likely positions and wraps them in § markers.

Original request:
POST /login
username=admin&password=password123

After adding positions:
username=§admin§&password=§password123§

Buttons:
Add §     — Wrap selected text as a payload position
Clear §   — Remove all positions
Auto §    — Let Burp guess positions automatically

Attack Types

Sniper       — One payload set, cycles through each position
               separately. Best for: testing single parameters.

Battering Ram — One payload set, inserts SAME value into ALL
               positions simultaneously.
               Best for: username == password tests.

Pitchfork    — Multiple payload sets (one per position), iterates
               them in parallel (list1[1] with list2[1], etc).
               Best for: username:password credential lists.

Cluster Bomb — Multiple payload sets, tries EVERY combination.
               Best for: brute forcing with separate wordlists.
               Warning: combinations grow very large fast.

Step 2 — Payloads Tab

Payload type options:

Simple list     — Enter a list of values manually or load from file
Runtime file    — Load from a file line by line
Numbers         — Generate number sequences (1,2,3... or 0-255)
Dates           — Date ranges
Brute forcer    — Generate all combinations of a charset
Username generator — Generate variations of a name

Common Wordlists (Kali Linux)

/usr/share/wordlists/rockyou.txt          — Passwords (14M entries)
/usr/share/seclists/Passwords/            — Many password lists
/usr/share/seclists/Usernames/            — Username lists
/usr/share/seclists/Discovery/Web-Content/common.txt  — Web paths
/usr/share/seclists/Fuzzing/              — Fuzzing payloads

Step 3 — Analyzing Results

In the results table, look for anomalies in:

Status code   — A 200 when others return 401 = valid login
Length        — Different response length = different behavior
               (A longer response often means valid data)
Time          — Slow response = possible blind SQL injection

Grep — Match: add the string you want to detect in responses
       (e.g. "Welcome", "Invalid password", "flag{")

Grep — Extract: pull a specific value from every response
       (useful for extracting tokens or data)

Brute Force Login Example

1. Capture a login POST request
2. Send to Intruder
3. Clear all § markers → select the password value → Add §
4. Attack type: Sniper
5. Payloads: Simple list → Load rockyou.txt
6. Options → Grep - Match → Add "Welcome" (or success string)
7. Start Attack
8. Sort by Length or Status — look for the outlier
Scanner — Finding Vulnerabilities

Active vs Passive Scanning

Passive Scan — Analyzes traffic that passes through the proxy without sending extra requests. Available in Community Edition. Flags obvious issues like missing security headers, cookies without HttpOnly, and cleartext passwords.

Active Scan — Sends crafted requests to actively probe for vulnerabilities. Professional Edition only. Detects SQL injection, XSS, SSRF, XXE, Path Traversal, and more.

Running a Passive Scan (Community)

Simply browse the target with Intercept off.
Burp passively analyzes every response automatically.

View findings:
Target → Site Map → select a host
Dashboard → Issue Activity (passive issues flagged in real time)

Running an Active Scan (Professional)

Method 1 — From Site Map:
Right-click a host or URL → Scan → Active Scan

Method 2 — From Proxy History:
Right-click a request → Scan

Method 3 — New Scan:
Dashboard → New Scan → enter URL → configure crawl and audit settings

Understanding Issue Severity

Critical  — Remote code execution, authentication bypass,
            direct database access
High      — SQL injection, stored XSS, SSRF, XXE
Medium    — Reflected XSS, CSRF, open redirect,
            sensitive data exposure
Low       — Clickjacking, missing security headers,
            information disclosure
Info      — Interesting observations — not vulnerabilities

Issue Details

For each finding Burp provides:
— Issue name and severity
— Affected URL and parameter
— Description of the vulnerability
— Remediation advice
— HTTP request/response that triggered it
— References (CWE, OWASP)
Decoder and Comparer

Decoder

Decoder lets you encode and decode data in many formats — essential for analyzing tokens, cookies, and obfuscated payloads.

Open: Decoder tab — or right-click any value → Send to Decoder

Supported formats:
URL encoding     — %20 %3D %2F ...
HTML encoding    — & < > ...
Base64           — dXNlcjpwYXNz ...
Base64 URL safe  — URL-safe variant used in JWTs
Hex              — 48 65 6c 6c 6f ...
Octal            — 110 145 154 154 157 ...
Binary           — 01001000 01100101 ...
Gzip             — Compressed data
Zlib             — Compressed data

Practical Decoder Uses

Decode a JWT token:
  Paste the JWT → Decode as Base64 URL
  Reveals: header.payload.signature in JSON

Decode a session cookie:
  Many frameworks base64-encode session data
  Paste cookie value → Decode as Base64

URL-decode a parameter:
  %3Cscript%3Ealert(1)%3C%2Fscript%3E
  → Decode as URL → <script>alert(1)</script>

Chain decodings:
  Some values are double-encoded
  Base64 → URL decode → HTML decode

Comparer

Comparer highlights the differences between two requests or responses — useful for spotting subtle changes that indicate different application behavior.

Open: Comparer tab — or right-click → Send to Comparer

Use cases:
— Compare two responses to find what changed between
  a valid and invalid login attempt
— Compare two requests to spot which parameter causes
  different behavior
— Compare the same endpoint with different privilege levels
  (admin vs regular user)

Two comparison modes:
Words — Highlights added/removed/changed words
Bytes — Highlights raw byte differences
Sequencer — Token Analysis

What is Sequencer?

Sequencer analyzes the randomness quality of tokens — session IDs, CSRF tokens, password reset tokens, and any other value that should be unpredictable. Weak randomness means tokens can be guessed or predicted.

Running a Sequence Analysis

1. Find a request that generates a token
   (login response with a session cookie, or a CSRF token endpoint)
2. Right-click the request → Send to Sequencer
3. In Sequencer → select the token field:
   — Under "Token Location Within Response"
   — Click "Configure" next to Cookie / Form field
   — Select the specific token value
4. Click "Start live capture"
   — Burp sends the request hundreds of times
   — Collects the token from each response
5. Click "Analyze now" after 100+ tokens

Reading the Results

Overall result:
"The overall quality of randomness is estimated to be: Excellent"
→ Token is cryptographically strong — not predictable

"The overall quality of randomness is estimated to be: Poor"
→ Token has patterns — potentially predictable — HIGH RISK

FIPS tests — Standard statistical tests for randomness:
— Monobit test
— Poker test
— Runs test
— Long runs test
Each shows pass/fail and a significance level

What Weak Tokens Mean

Sequential tokens:   session=1001, session=1002 ...
                     → Enumerate other users' sessions

Time-based tokens:   token = base64(timestamp)
                     → Predict future tokens

Short tokens:        4-character hex = 65536 possibilities
                     → Brute forceable in seconds

Target → Site Map

Color coding:

Testing Common Vulnerabilities

SQL Injection

1. Find a parameter that queries the database (id, search, user)
2. Send the request to Repeater
3. Add a single quote: id=1'
   — Server error or different response = possible SQLi

Common payloads:
id=1 OR 1=1--
id=1' OR '1'='1'--
id=1 UNION SELECT null--
id=1 UNION SELECT null,null--
id=1 UNION SELECT table_name,null FROM information_schema.tables--

Time-based blind:
id=1; SLEEP(5)--      (MySQL)
id=1; pg_sleep(5)--   (PostgreSQL)
id=1; WAITFOR DELAY '0:0:5'--  (MSSQL)

Cross-Site Scripting (XSS)

1. Find inputs reflected in the response (search, name, comment)
2. Send to Repeater → inject payloads

Basic payloads:
<script>alert(1)</script>
<img src=x onerror=alert(1)>
<svg onload=alert(1)>
"><script>alert(1)</script>
'><script>alert(1)</script>

Filter bypass:
<ScRiPt>alert(1)</ScRiPt>
<script>alert`1`</script>
<details open ontoggle=alert(1)>
javascript:alert(1)

IDOR — Insecure Direct Object Reference

1. Find requests that reference an object by ID
   /api/orders/1042
   /download?file=invoice_1042.pdf
   /user/profile?id=1042

2. Send to Repeater → change the ID
   /api/orders/1041   — another user's order?
   /api/orders/1043

3. If you get another user's data = IDOR vulnerability

Horizontal IDOR:   Access same-privilege user's data
Vertical IDOR:     Access higher-privilege data (admin panel)

CSRF — Cross-Site Request Forgery

1. Find a state-changing request (change email, transfer funds)
2. Send to Repeater
3. Remove the CSRF token from the request
   — If it still works = CSRF vulnerability
4. Change the token to an invalid value
   — If it still works = token not validated

Generate CSRF PoC (Professional):
Right-click request → Engagement tools → Generate CSRF PoC
Burp creates an HTML page that auto-submits the request

Directory Traversal

1. Find file inclusion parameters
   /download?file=report.pdf
   /view?page=home

2. Test traversal payloads:
   ../../../etc/passwd
   ....//....//....//etc/passwd
   ..%2F..%2F..%2Fetc%2Fpasswd     (URL encoded)
   %2e%2e%2f%2e%2e%2fetc%2fpasswd  (double encoded)
   /etc/passwd                      (absolute path)

Windows targets:
   ..\..\..\Windows\System32\drivers\etc\hosts

SSRF — Server-Side Request Forgery

1. Find parameters that fetch a URL or resource
   url=https://example.com/image.jpg
   webhook=https://api.target.com/notify
   fetch=http://internal-service/data

2. Test with internal addresses:
   url=http://127.0.0.1
   url=http://localhost
   url=http://169.254.169.254         (AWS metadata)
   url=http://169.254.169.254/latest/meta-data/
   url=http://192.168.1.1             (internal network)
   url=file:///etc/passwd             (local file read)
Extensions — BApp Store

What are Extensions?

Burp Suite's functionality can be extended with plugins written in Java, Python, or Ruby. The BApp Store has hundreds of community and PortSwigger-made extensions — many are free.

Extensions → BApp Store → Browse and install

Essential Free Extensions

Logger++
  — Advanced request/response logging with powerful filters
  — Much better than the built-in Proxy history
  — Allows regex-based searching across all traffic

Retire.js
  — Detects JavaScript libraries with known vulnerabilities
  — Passively scans every JS file loaded by the target

JWT Editor
  — Decode, modify, and re-sign JSON Web Tokens
  — Test for algorithm confusion (RS256 → HS256 attack)
  — Test for "none" algorithm vulnerability
  — Embedded JWKS injection

Param Miner
  — Discovers hidden and unlinked parameters
  — Tests for web cache poisoning
  — Finds parameters not visible in the normal interface

Autorize
  — Automates privilege escalation testing (IDOR/BOLA)
  — Repeats every request with a lower-privileged token
  — Flags requests where the response is identical

Hackvertor
  — Advanced encoding and transformation chains
  — Custom tags for complex encoding/decoding
  — Useful for WAF bypass payloads

Active Scan++
  — Adds extra active scan checks not in the default scanner
  — Finds template injection, host header injection, and more

CSRF Scanner
  — Passively flags requests missing CSRF protection

Software Vulnerability Scanner
  — Maps detected software versions to CVE database

HTTP Response Codes Quick Reference

200  OK                    — Request succeeded
201  Created               — Resource created
301  Moved Permanently     — Redirect
302  Found (Redirect)      — Temporary redirect
400  Bad Request           — Malformed request
401  Unauthorized          — Authentication required
403  Forbidden             — Authenticated but no permission
404  Not Found             — Resource doesn't exist
405  Method Not Allowed    — Try different HTTP method
429  Too Many Requests     — Rate limiting
500  Internal Server Error — Server-side error (possible vuln)
502  Bad Gateway           — Upstream server issue

Testing Checklist for Every Web App

 Browse entire application with Intercept off (build Site Map)
 Identify all input points (forms, URL params, headers, cookies)
 Test each input for SQL injection
 Test each reflected input for XSS
 Test file upload functionality
 Test IDOR on all object references
 Check for CSRF on all state-changing requests
 Test authentication (brute force, default creds, lockout)
 Check for sensitive data in responses (tokens, keys, PII)
 Check security headers (Passive scan findings)
 Test for path/directory traversal on file parameters
 Check for SSRF on URL parameters
 Inspect JavaScript files for hidden endpoints and keys
 Test authorization — access other users' resources
 Check cookies for Secure, HttpOnly, SameSite flags
