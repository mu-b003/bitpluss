Nmap Activity Detection

You can carry out this task practically in an isolated virtual lab if you don't have one you can set up your own using this link.

Commands: These are sudo apt update then sudo apt upgrade -y used to update the system before the exercise begins. Result: 12 upgradeable packages are available, and a 4,588 kB update download has begun — the system is in routine update mode.

Commands: These are sudo apt install apache2 -y then start/status apache2 used to verify that the Apache server is running as the target for testing. Result: apache2 is pre-installed, the service has been active (running) for two days, with a recent reload log dated July 21 at 17:53 .

Commands: These are sudo apt install openssh-server -y then start/status ssh used to verify that the SSH service is running as a second target for testing. Result: openssh-server is pre-installed, and the service was recently started (active just 11 seconds ago) — a deliberate restart prior to the exercise.

The command: ip a is used to display the IP address of the Ubuntu machine (the target). The result: the ens33 interface displays the address 192.168.81.129/24— the same target address used in subsequent Nmap operations.

Commands (from Kali): These are sudo apt updatethen sudo apt upgrade -y used to update the Kali system in preparation for running the scanning tools. Result: All packages are up to date.

The command: sudo apt install nmap wireshark -y Used to ensure that both Nmap and Wireshark are installed together on Kali. Result: Both tools are pre-installed with the latest version (nmap 7.99, wireshark 4.6.6) — ready to use.

The command: sudo wireshark on Ubuntu. Used to open Wireshark in preparation for capturing incoming Nmap traffic. Result: Attempt to open previous capture files failed (not found) because they were previously on a different machine, with the ens33 interface selected to start a new capture.

Commands (from Kali): These are nmap -sn 192.168.81.129 then nmap 192.168.81.129 used to perform a host discovery scan (Ping Scan) followed by a default scan of common ports. The result: confirmation that the host is up, and the discovery of two open ports: 22/tcp (ssh) and 80/tcp (http) .

Commands: These are sudo nmap -sS 192.168.81.129then sudo nmap -sV 192.168.81.129 used to perform a SYN scan followed by a scan to detect service versions. The result: Confirmation of the same two open ports, with the versions precisely identified: OpenSSH 10.2p1 Ubuntu 2 Ubuntu 3.5 and Apache httpd 2.4.66 .

The command: sudo nmap -A 192.168.81.129 Used to perform an aggressive comprehensive scan combining service discovery, operating system, and traceroute. The result: Confirmation of both services with details of the default Apache page, a detailed Linux operating system fingerprint, and a single-hop (0.96ms) traceroute path.

The command: sudo nmap -p- 192.168.81.129 Used to scan all 65535 ports instead of just the common ones, to ensure there are no additional hidden ports. Result: Confirmation of only two open ports (22 and 80) out of 65535 ports. The scan was completed in 4.48 seconds.

A Wireshark window view after capturing has stopped, showing the traffic generated by all previous Nmap operations (especially the full port scan -p-). The result: a massive amount of packets ( 139,970 packets ) — a SYN pattern from a fixed port (55421) corresponding to RST,ACK for randomly sequenced destination ports at very high speed — a clear signature of a full Nmap port scan.

Menu: File > Save As in Wireshark. Used to initiate saving the capture file that documents the entire Nmap activity.

The Save Capture File As window, with a path /home/soc-lab/Desktopand filename nmap-activity-detection.pcapng. The result: The file is saved with a name that clearly reflects the nature of the exercise (detecting Nmap activity), ready for subsequent statistical analysis like previous exercises.

Menu: Statistics > Capture File Properties (selected) for the nmap-activity-detection.pcapng file. Used to access full capture statistics.

Capture File Properties window. The result: a large file size of 12 MB , with a huge number of packets (139,970 packets ) over a relatively short period (00:03:53 ) , with a very high average rate of 598.3 packets/second and a data rate of 278 kbps — much higher than the previous two exercises (Network Analysis and Port Scan), reflecting the intensity of the comprehensive Nmap scan of all ports.

Menu: Statistics > Protocol Hierarchy (selected). Used to display the distribution of protocols in this large capture.

Protocol Hierarchy Statistics window. The result: TCP dominates with 99.9% of the packets (139,825 packets) — a higher percentage even than the previous Port Scan exercise (98.3%), confirming that the comprehensive scan of all ports ( -p-) generated a much larger volume of raw TCP traffic.

Menu: Statistics > Endpoints (selected). Used to navigate to view endpoint statistics.

Endpoints window, IPv4·11 tab. The result: Kali and Ubuntu machines (192.168.81.128 and 192.168.81.129) captured almost all the traffic with an almost identical size of 8 MB each and a number of packets exceeding 139,800 per machine — almost a total focus on these two ends only.

Menu: Statistics > Conversations (selected). Used to navigate to view the main conversation details.

Conversations window, IPv4·11 tab. The result: The main conversation between 192.168.81.128 and 192.168.81.129 with a massive size of 8 MB and a number of 139,849 packets in only 4 streams — an unprecedented size that clearly surpasses any normal traffic, as confirmed by a thorough and intensive Nmap scan.

A filter application tcpshows a very rapid sequence of SYN packets from multiple and varied ports (135, 554, 8080, 25, 23, 8888, 1720, 1025...) from the same source port (48976) within fractions of a second. The result: a very rapid, comprehensive scan pattern covering a wide and random range of port numbers—perfectly matching the nmap -p-previously executed command.

Filter application: tcp.flags.syn == 1 && tcp.flags.ack == 0 Used to isolate only all initial SYN attempts. The result: A very large number of pure SYN packets — 69,643 packets (49.8%) of the total capture, meaning that almost half of all captured motion was just initial screening attempts.

Filter application: tcp.flags.syn == 1 && tcp.flags.ack == 1 Used to isolate positive SYN-ACK responses (ports that are actually open). Result: Only 93 packets (0.1%) of type SYN-ACK — a very small percentage compared to the enormous size of SYN — confirming that most of the 65,535 ports were closed, and only ports 22 and 80 were actually open.

Filter application: tcp.flags.reset == 1 Used to isolate RST (closed port responses) packets. The result: A huge number of RST,ACK packets — 69,591 packets (49.7%) , almost half of all traffic, conclusive evidence of a thorough scan targeting almost the entire port range and encountering closed ports in the vast majority of attempts.

Filter application: tcp.port == 22 Used to isolate SSH port traffic within this comprehensive scan. Result: Displaying only 302 packets (0.2%) out of a total of 139,970 — a recurring pattern of SYN→SYN-ACK→RST for multiple scan attempts, interspersed with actual successful SSH connections (SSH-2.0-OpenSSH Server Protocol) amidst the noise, illustrating the vast difference between the total scan traffic volume and the traffic volume of a single open port.

Filter application: tcp.port == 80 used to isolate HTTP port traffic within this comprehensive scan. Result: Only 443 packets (0.3%) were displayed , all containing the same recursive scan pattern (SYN/SYN-ACK/RST), in addition to a complete and successful HTTP connection (GET/HTTP/1.0 with 200 OK responses) — the analysis concludes by showing that out of approximately 140,000 packets, there were only two genuine application connections (SSH and HTTP) amidst a vast sea of ​​Nmap's comprehensive port scanning attempts.
