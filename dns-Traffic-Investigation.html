DNS Traffic Investigation

This task can be performed practically in an isolated lab if you do not have a lab you can create one using this link.

Commands: sudo apt update Then, sudo apt upgrade -y on an Ubuntu machine (soc-lab), they were used to update the system before starting the investigation. Result: One upgradeable package was detected, but the system did not upgrade it due to the "phasing" mechanism of the snapd package — Summary: 0 upgrades, 0 installations, 0 removals, 1 unupgraded.

Commands: ip aOn an Ubuntu machine, used to check network settings before starting DNS traffic capture. Result: ens33Active interface with a dynamic IP address 192.168.81.129/24, as well as a loopback interface.

Commands: sudo apt update Then, sudo apt upgrade -yon the Kali machine, they were used to update the system before investigation. Result: All packages are already up to date ( All packages are up to date), and nothing has been upgraded.

Commands: sudo apt install dnsutils -y Then, nslookup bitpluss.comon Kali, install DNS tools and test the target domain analysis. Result: Installed bind9-dnsutils(which is the alternative package), analysis bitpluss.comreturned Cloudflare addresses (IPv4 and IPv6).

Commands: sudo apt install wireshark -y On Ubuntu, to ensure the package analyzer is available. Result: Wireshark is pre-installed and is the latest version (4.6.4-1), no installation required.

Commands: sudo wireshark To run the tool with administrator privileges. Result: The Wireshark welcome screen opened with a list of available capture interfaces, and one interface was selected as the ens33target capture interface for monitoring DNS traffic.

Commands: A series of commands nslookup on Kali for three domains: bitpluss.com, github.com, ubuntu.com. Result: Each domain was successfully resolved via the local DNS server (192.168.81.2), with multiple IPv4 and IPv6 addresses returned for each domain.

Commands: dig bitpluss.com On Kali, to perform a detailed DNS query. Result: A detailed view including the Answer section, the Authority section showing Cloudflare name servers, and an Additional section with the addresses of those servers.

Commands: Loop for domain in google.com github.com microsoft.com openai.com ubuntu.com kali.org; do nslookup $domain; doneon Kali. Result: Starting to execute successive DNS queries for several known domains (google.com, github.com, microsoft.com...) to generate clean DNS traffic for later comparison.

Continued view of the same previous episode. Result: Successful completion of the analysis results for the remaining domains (microsoft.com, openai.com, ubuntu.com, kali.org), confirming legitimate DNS traffic.

Commands: nslookup fake-domain-12345.local On Kali, to simulate a query for a non-existent domain. Result: Resolution failed with a message NXDOMAIN, documenting DNS behavior when requesting a fake/non-existent domain.

Commands: Live Capture via Wireshark on an ens33 Ubuntu interface. Result: Recording of various traffic including DNS queries, TCP/HTTP connections, NTP and ARP packets, including the capture fake-domain-12345.local and failure of a query (NXDOMAIN) within packets 2189–2190.

Commands: Open a menu File in Wireshark while live capture is ongoing, preparing to save the file. Result: Save options ( Save, Save As...) appear as packets continue to flow (counter reaches 2212 packets).

Commands: Used Save Asin Wireshark to save the capture. Result: The path and filename were specified in an uncompressed format./home/soc-lab/Desktopdns-traffic-investigation.pcapng

Commands: Open a menu Statisticsin Wireshark after saving the file dns-traffic-investigation.pcapng. Result: Displays a list of available statistical options (Capture File Properties, Protocol Hierarchy, Conversations, Endpoints... etc.) in preparation for analyzing the captured packets.

Commands: Statistics > Capture File Properties on a file dns-traffic-investigation.pcapng. Result: Display full file details — 2212 packets, size 2,157 KB, capture time 00:07:46 , average 4.7 packets/second and 35 KB/second.

Commands: Statistics Reopen the menu by hovering the cursor over an option Protocol Hierarchy. Result: Prepared to display the protocol hierarchy within the captured file.

Commands: Statistics > Protocol Hierarchy. Result: Protocol distribution — IPv4 accounts for 97.8% of the packets, TCP accounts for 90.8%, while TLS accounts for 94.3% of the total bytes, and DNS accounts for only 2.4% of the packets.

Commands: Open a menu Statistics by hovering the cursor over an option Endpoints. Result: Prepares to display a list of endpoints involved in the captured motion.

Commands: Statistics > Endpoints. Result: Displaying 13 IPv4 endpoints with packet/byte details for each address — highlighting 151.101.210.491,990 packets (2 MB) and 192.168.81.129(the Ubuntu machine itself) 2,091 packets (2 MB).

Commands: Open a menu Statistics by hovering the cursor over an option Conversationsin Wireshark on a file dns-traffic-investigation.pcapng. Result: Prepared to display the recorded network conversations between the different parties in the capture.

Commands: Statistics > Conversations With the IPv4 tab displayed. Result: Displaying 12 IPv4 conversations — the most notable being a conversation 192.168.81.129with 151.101.210.49a size of 2 MB and a relatively high transfer speed (79 kbps / 4,540 kbps), along with smaller NTP and DNS conversations.

Commands: Applying the display filter dnsin Wireshark. Result: Displaying 52 DNS packets (2.4% of the total) including queries and responses for multiple domains (github.com, ubuntu.com, bitpluss.com, cdn.fwupd.org...), with detailing response packet number 101 for the AAAA query for cdn.fwupd.org.

Commands: Apply a filter dns.flags.response == 0 to display only outgoing DNS queries (not responses). Result: Displays 30 query packets (1.4%), including normal queries for known domains plus the last suspicious query fake-domain-12345.localin packet 2189.

Commands: Apply a filter dns.flags.response == 1 to display DNS responses only. Result: Display 26 response packets (1.2%), including the final response to fake-domain-12345.localpacket 2190 which shows a "No such name" error (NXDOMAIN) along with successful responses for other domains.

Commands: Apply a filter dns.qry.type == 1 to display only A-type queries. Result: Displays 28 packets (1.3%) representing A-record queries and responses for domains such as bitpluss.com, github.com, microsoft.com, kali.org, and others.

Commands: Apply a filter dns.qry.type == 28 to display only AAAA (IPv6) type queries. Result: Displays 24 packets (1.1%) representing AAAA-record queries and responses, with ubuntu.com's response details containing multiple IPv6 addresses.

Commands: Apply a filter udpto display all UDP traffic in the file. Result: Displays 157 packets (7.1%) including a mix of DNS and NTP traffic, illustrating the transition from recent DNS queries to the beginning of recurring NTP (NTS) packets between the machine and external servers.

Commands: Apply a filter udp.port == 53 to display DNS traffic exclusively over port 53. Result: Display 52 packets (2.4%), matching the results of the dnsprevious filter, confirming that all DNS traffic is passing through UDP/53 as expected.

Commands: Apply a filter dns.flags.rcode != 0to isolate responses containing an error code (not a success). Result: Displaying only one packet (0.0%), which is the response to fake-domain-12345.local(package 2190), confirming that it is the only query in the entire capture that failed with a "No such name" error — the key evidence documented in this DNS Traffic Investigation Task .
