SOC-Failed-Login-Incident-Response

Open the terminal and type ip a to find the IP address. As it appears in the terminal, the IP address is 192.168.150.129 on the victim's machine.

Also, open the terminal on the attacker's Kali machine and type ip a. The IP address that appears in the terminal is 192.168.150.130.

We type the command ping to confirm the connection to the victim's device: ping -c 192.168.150.129

Use `sudo apt update` to update the list of packages available in the system repositories to ensure you have the latest version of the software.

`sudo apt install openssh-server -y` is the basic command for installing an SSH server.

The openssh-server package is responsible for allowing the device to accept SSH connections from other devices.

-y is short for automatic yes approval

`sudo systemctl enable ssh --now` This command performs two functions: `enable` makes the service start automatically when the system boots, and `--now` starts the service immediately without requiring a restart.

`sudo systemctl status ssh` This command is used to verify that the service is working correctly.

Statuses: Read service status active, listening

We use Secure Copy SCP to transfer files securely via the SSH protocol.

sudo soc-analyst@192.168.150.129:/var/log/auth.log ~/auth_capture.log

Here we specify the user and their device: soc-analyst@192.168.150.129

var/log/auth.log/ is the source path of the file located on the victim's device.

Log files are the most important system log files in Linux. This file contains details of successful and failed logins.

The path where the file is saved within your Kali device is ~/auth_capture.log. It is saved in home.

We use `ls -l` to display folders and files; here we want to find the location of the auth_capture.log file.

The `mkdir project` command creates a folder because we will be moving the auth_capture.log file to this `project` folder.

mv auth_capture.log project/ to move the file to the folder

We run the command `sudo tail -f /var/log/auth.log` to monitor live logs on the victim's machine.

The tail tool displays the end of the file, the last line.

-f (follow) This command option continues to monitor the file and display any new updates that appear in it in real time.

var/log/auth.log/ This is the authentication log file that contains login events.

In this step, we prepare for the brute force attack or dictionary attack.

We create a file, for example, named touch passwords.txt lgt thvy

After creating the file, we use the nano passwords.txt command to open it. Then, we write a list of passwords. Enter incorrect passwords because we want to perform a failed login test.

For example, we write random passwords, provided they are incorrect.

password

123456

user

At this stage, we execute a brute-force attack using the Hydra tool.

hydra -lsoc-analyst -P passwords.txt ssh://192.168.150.129 -t 4 pV

-l soc-analyst Target username

-P passwords.txt Specifies the dictionary file containing the passwords that Hydra will try.

ssh://192.168.150.129 Specify the SHH service and the target device's address

-t 4 is the number of parallel attempts, and we chose 4 to increase the attack speed simultaneously.

-V (verbos mode) to display the system's every attempt in detail

The outputs inside the orange box are the direct result of the brute-force attack we performed using Hydra

Authentication failure: This line is repeated several times and means that the system rejected login attempts because the password is incorrect.

Password check failed for user soc-analyst. This line confirms that the system attempted to verify the password for user soc-analyst and failed each time.

Failed password for soc-analyst from 192.168.150.130. Here, the source of the attack is identified (and the IP address of the target device is 192.168.150.130) and the username of the target.

Activating IPv4 penalty... for penalty: failed authentication. Here, the system blocked the IP for 17 seconds. This is the most important security point in the log. The system detected an attack with multiple failed attempts in a short period of time.

In this step, we want to speed up the analysis, so we will create and name a file named failed_login_analyzer.py

touch faile_login_analyzer.py

Open this file to write the script inside: nano failed_login_analyzer.py

Currently, we might not need this script for this task, but if there is a large amount of data, it can be difficult to handle manually, so using a script like this could be very helpful.

analyzer.py

python3 failed_login_analyzer.py --log auth_capture.log --threshold 5 --output report.cvs

The Python3 interpreter that requests the operating system to run the Python file.

failed_login_analyzer.py is the name of the script we programmed; it's the file that contains the programming logic.

--log auth_capture.log This is an argument parameter that tells the script the path to the log file we want to parse.

--threshold 5 This is a parameter that determines the level of risk. The script tells us if it finds any IP address with 5 or more failed attempts and classifies it as a high risk (HIGH).

--output report.csv This parameter specifies the filename that Script will create to save the final results.

In this step, we will take a defensive measure on the victim's device to secure the system.

The command `sudo ufw status` is used to check the firewall's status. As you can see, the result shows `Status: inactive`, meaning the firewall was inactive, which exposed the system to the attacks we previously carried out.

`sudo ufw enable` This command activates the firewall, and as you can see, immediately after executing it, the message "Firewall is active and enabled on system startup" appears.

sudo ufw deny from 192.168.150.130

This step is the incident response step. After identifying the attacker's IP address, we issue a command to the firewall to permanently block that IP. The result is a "Rule added"—a blocking rule that prevents any future communication from this attacker.

sudo ufw status numbered

This command displays a list of all UFW firewall rules, and the result shows leader number 3 DENY IN for IP address 192.168.150.130

`sudo nano /etc/ssh/sshd_config` opens the configuration file by typing this command to implement certain security practices to reduce the attack surface.

Changing the default SSH port from 22 to 2222 prevents automated attacks that only search for default ports.

The change "permitRootLogin no" is very important as it prevents an attacker from attempting to log in directly with root privileges.

`sudo ufw allow 2222/tcp` tells the firewall to open the new port to allow incoming SSH connections.

`sudo ufw delete allow 22/tcp` This command deletes the old permission that allowed connections over the default port 22.

`sudo systemctl restart ssh` This command restarts the SSH service on the system and activates the changes we made in the configuration file.
