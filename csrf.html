Cross-Site Request Forgery (CSRF)

Cross-Site Request Forgery (CSRF) is a web vulnerability that forces a victim's browser to perform unwanted actions on a web application where the victim is already authenticated.

The attack abuses the trust that a website places in a user's browser.

Why Is CSRF Dangerous?

An attacker may be able to:

• Change account settings

• Change passwords

• Transfer funds

• Send messages

• Perform actions as the victim

How CSRF Works

1- The victim logs into a website.

2- The website creates a session cookie.

3- The victim visits an attacker-controlled website.

4- The attacker's page sends a request to the target website.

5- The browser automatically includes the victim's cookies.

6- The target website processes the request as if it came from the victim.

Example Scenario

The victim is logged into:

https://bank.com

The application uses cookies for authentication.

The attacker creates a malicious page that submits:

POST /transfer
amount=1000
account=attacker

If protections are missing, the transfer may be executed using the victim's session.

Why Cookies Matter

Browsers automatically send cookies with requests.

Cookie: session=abc123

CSRF attacks rely on this behavior.

Conditions Required for CSRF

• The victim must be authenticated.

• Authentication relies on automatically sent credentials.

• The application does not properly verify requests.

Example Vulnerable Request

POST /change-email

email=attacker@example.com

If no CSRF protection exists, an attacker may trigger this request from another website.

GET-Based CSRF Example

https://example.com/delete?id=10

If sensitive actions use GET requests, exploitation may become easier.

CSRF Attack Example

Malicious HTML page:

<form action="https://example.com/change-email"
method="POST">

  <input type="hidden"
  name="email"
  value="attacker@example.com">

</form>

The browser may automatically submit the request with the victim's session cookie.

CSRF Tokens

The most common defense against CSRF.

The application generates a unique random token for each user session.

Example:

<input type="hidden"
name="csrf_token"
value="a8f9c7e123">

The server validates the token before processing the request.

SameSite Cookies

The SameSite attribute controls whether cookies are sent with cross-site requests.

Example:

Set-Cookie:
session=abc123;
SameSite=Strict

Possible values:

• Strict

• Lax

• None

Origin Header

The Origin header identifies the source of a request.

Origin: https://example.com

Applications may validate this header to help prevent CSRF attacks.

Referer Header

The Referer header indicates the page that initiated the request.

Referer: https://example.com/profile

Some applications validate it as an additional defense.

Impact of CSRF

• Account takeover assistance

• Unauthorized transactions

• Configuration changes

• Data modification

• Unauthorized actions

Preventing CSRF

CSRF Tokens

Use unpredictable anti-CSRF tokens.

SameSite Cookies

Restrict cross-site cookie usage.

Origin Validation

Verify the Origin header.

Referer Validation

Verify the Referer header when appropriate.

Re-authentication

Require password confirmation for sensitive actions.

What Should a Penetration Tester Check?

• Are CSRF tokens implemented?

• Are CSRF tokens validated?

• Are tokens predictable?

• Can tokens be reused?

• Are sensitive actions protected?

• Is SameSite configured correctly?

• Are Origin and Referer validated?

• Can requests be executed from another website?

CSRF Testing Workflow

1- Identify state-changing functionality.

2- Capture the request using Burp Suite.

3- Check for CSRF protections.

4- Analyze token implementation.

5- Attempt to reproduce the request from another origin.

6- Verify whether the action succeeds.

Important Note

CSRF attacks target authenticated users.

Unlike XSS, the attacker does not need to execute JavaScript on the vulnerable website.

The attack relies on the browser automatically sending authentication credentials.
