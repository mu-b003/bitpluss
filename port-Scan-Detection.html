Port Scan Detection

The command: This is sudo apt updatethen sudo apt upgrade -y used to update the package lists and ensure the system is up to date before starting the exercise. Result: All packages are up to date — the system is ready to begin.

Commands: These are sudo apt install apache2 -ythen enable/status apache2 used to verify that the Apache server is installed and running as the target service for testing. Result: apache2 is pre-installed, and the service has been active (running) for about 1 day and 4 hours — with a recent reload history dated July 20.

Commands: These are sudo apt install openssh-server -ythen enable/status ssh used to verify that the SSH service is enabled as a second target service for testing. Result: openssh-server is pre-installed, the service is active (running), with a previous successful login for user Mubarak from 192.168.81.128.

The command: ip a is used to display the IP address of the Ubuntu machine (the target). The result: the ens33 interface displays the address 192.168.81.129/24— which is the same target address used in subsequent scans.

Commands (from Kali): These are sudo apt updatethen sudo apt upgrade -y used to update the Kali system and prepare it with the scanning tools before performing a port scan. Result: 37 packages successfully updated on the Kali machine with a download size of 8,633 kB.

The command: sudo apt install nmap -y Used to verify that the Nmap tool is installed to perform a port scan. Result: Nmap is pre-installed with the latest version (7.99+dfsg-1kali1) — the tool is ready to use.

The command: sudo apt install wireshark -y Used to verify that Wireshark is installed on the Ubuntu machine to capture and monitor scan activity. Result: Wireshark is pre-installed with the latest version (4.6.4-1) — ready to begin monitoring.

Commands: These are sudo systemctl status sshthen status apache2 used for a final check of the status of both target services before the scan begins. Result: Both services (SSH and Apache2) are stablely running—the targets are fully ready to receive scan attempts.

The command: sudo wiresharkon Ubuntu. Used to open Wireshark and start preparing to capture incoming motion during an Nmap process. Result: Automatically opens the previous capture file network-analysis.pcapng(273 KB), with the ens33 interface selected to prepare for a new capture.

The command (from Kali): nmap 192.168.81.129 Used to perform a default scan to detect open ports on the target. Result: Two open ports detected: 22/tcp (ssh) and 80/tcp (http) — scan completed in just 0.82 seconds.

Command: sudo nmap -sS 192.168.81.129 Used to perform a stealth scan (SYN Stealth Scan) that does not complete a full TCP handshake, to reduce the likelihood of detection. Result: Same as before — ports 22/tcp and 80/tcp open, scan completed in 0.81 seconds.

The command sudo nmap -sV 192.168.81.129 is used to detect service versions running on open ports. The result: Accurately identifies the services — OpenSSH 10.2p1 Ubuntu 2ubuntu3.4 on port 22, and Apache httpd 2.4.66 on port 80, with the operating system identified as Linux.

The command: sudo nmap -O 192.168.81.129 is used to attempt to discover the operating system by analyzing the TCP/IP packet fingerprint. The result: No exact match for the operating system was found, but a detailed fingerprint of the network stack was displayed, with the network distance specified as (Network Distance: 1 hop).

The command: sudo nmap -A 192.168.81.129 Used to perform an aggressive scan combining service discovery, operating system, Traceroute, and SNMP scripts. The result: Service confirmation (OpenSSH and Apache) with additional details such as the homepage title "Apache2 Ubuntu Default Page: It works" and a one-hop Traceroute path with a response time of 0.51ms.

Wireshark window view during actual capture (Capturing from ens33) on an Ubuntu machine. The result: a huge number of red TCP packets (SYN from Kali corresponding to RST,ACK from Ubuntu) on multiple random and consecutive ports — a classic pattern documenting an actual port scan , with a total of 11,119 captured packets.

Menu: File > Save As in Wireshark. Used to start the process of saving the capture file that documents the detected scanning activity.

The Save Capture File As window, with a path /home/soc-lab/Desktopand filename port-scan-detection.pcapng. The result: the file is saved alongside the previous capture file network-analysis.pcapng— the filename clearly reflects the nature of the exercise (port scanning detection).

Menu: Statistics > Capture File Properties (selected). Used to access the statistics of the newly saved port-scan-detection.pcapng file.

Capture File Properties window for the port-scan-detection.pcapng file. The result: a relatively large file size of 1,182 kB , with 11,129 packets in just a short time (00:06:35 ) , with a high average rate of 28.1 packets/second — an unusual rate that clearly reflects the intensity of port scanning traffic compared to normal traffic in the previous exercise.

Menu: Statistics > Protocol Hierarchy (selected) for the port-scan-detection.pcapng file. It is used to display the distribution of protocols in the traffic associated with the scan, and in the background, various packets (NTP, ARP, DNS PTR queries, TCP SYN for multiple ports such as 80, 8080, 445) are shown — documenting the network reconnaissance patterns associated with the entire Port Scan process.

Protocol Hierarchy Statistics window for port-scan-detection.pcapng. The result: TCP accounts for the overwhelming majority of packets (10,935 packets) at 98.3% , while the actual service protocols (SSH and HTTP) account for only a very small percentage (0.3% and 0.7% respectively) — a significant difference between the raw TCP traffic volume and the actual application traffic volume, a classic indicator of Port Scan activity rather than normal application connections.

Menu: Statistics > Conversations (selected). Used to navigate to view conversation details and analyze communication patterns between devices.

Conversations window, Ethernet·10 tab. The result: The largest conversation between the MAC addresses of Kali and Ubuntu, with a size of 794 kB and a huge number of packets (11,003 packets) — a size completely disproportionate to the nature of normal network traffic, confirming the presence of an intensive scanning process.

Menu: Statistics > Endpoints (selected). Used to navigate to view endpoint statistics (participating devices) in the capture.

Endpoints window, Ethernet tab·8. The result: Kali and Ubuntu machines (00:0c:29:2b:4f :ef and 00:0c:29:3f:90 :98 ) captured the vast majority of the traffic with a similar size (812 kB and 797 kB) and a number of packets exceeding 11,000 each — confirming that almost the entire capture is related to the scanning process between these two machines only.

A filter application tcpfocusing on the sequential SYN packets to multiple ports (80, 8080, 445, 111...) from the same source port (48711) at very short intervals (fractions of a millisecond). The result: This pattern—a fixed source port sending SYN packets sequentially and rapidly to multiple, different destination ports—is the classic signature of an automated TCP port scanning process (not a normal user connection).

Advanced filtering application: tcp.flags.syn == 1 && tcp.flags.ack == 0 Used to isolate only pure SYN packets (the beginning of connection attempts) to identify all scanned ports. Result: 5,168 packets (46.4% of the total capture) are pure SYN attempts for consecutive, random ports—a huge number confirming systematic and comprehensive scanning activity across most of the port range.

Filter application: tcp.flags.syn == 1 && tcp.flags.ack == 1 Used to isolate positive responses (SYN-ACK) indicating that the target ports are actually open . Result: Only 128 packets (1.2%) were of type SYN-ACK — meaning that a very small number of scanned ports were actually open (corresponding to ports 22 and 80 previously detected by Nmap), while the rest were closed.

Filter application: tcp.flags.reset == 1 Used to isolate RST packets representing closed port responses to connection attempts. Result: A large number of RST,ACK packets ( 5,110 packets, 45.9% ) — representing Ubuntu's immediate responses to each SYN attempt on a closed port, providing further strong evidence of a comprehensive scan of a wide range of ports.

Filter application: tcp.port == 22 Used to isolate all traffic associated with a specific SSH port during the scan. The result: A recurring sequence of SYN→SYN-ACK→RST attempts from different source ports repeatedly targeting port 22 (a recurring scan pattern for the same port), with a single successful packet containing the actual SSH Protocol Server response appearing amidst the noise—representing the real connection amidst the repeated scan attempts.

Filter application: tcp.port == 80 Used to isolate all traffic associated with a specific HTTP port during the scan. The result: The same SYN/SYN-ACK/RST pattern repeated across multiple attempts, interspersed with a complete and successful HTTP connection (GET/HTTP/1.0 versus 200 OKs) — clearly demonstrating how a genuine application connection can be distinguished amidst the noise of repeated scan packets.
