OAuth 2.0

OAuth 2.0 is an authorization framework that allows applications to access resources on behalf of a user without knowing the user's password.

It is commonly used for "Login with Google", "Login with GitHub", and API access delegation.

Why Use OAuth 2.0?

Without OAuth, users would have to share their passwords with third-party applications.

OAuth allows limited access using tokens instead of credentials.

Main Components

Resource Owner

The user who owns the data.

Client

The application requesting access.

Authorization Server

The server responsible for authenticating users and issuing tokens.

Resource Server

The API or service that stores protected resources.

OAuth 2.0 Flow

1- User clicks "Login with Google".

2- User is redirected to the Authorization Server.

3- User authenticates and grants permission.

4- Authorization Server issues an Authorization Code.

5- Client exchanges the code for an Access Token.

6- Client uses the token to access protected resources.

Resource Server (API)

Access Token

An Access Token is a temporary credential used to access protected resources.

Example:

Authorization: Bearer eyJhbGciOiJIUzI1NiIs...

Refresh Token

A Refresh Token is used to obtain a new Access Token when the current one expires.

This allows users to stay logged in without re-entering credentials.

Scopes

Scopes define what permissions the application receives.

Examples:

read:profile
read:email
write:posts

The application should only request the permissions it actually needs.

Common Grant Types

Authorization Code Grant

The most secure and most commonly used flow.

Recommended for web and mobile applications.

Client Credentials Grant

Used for server-to-server communication.

No user interaction is required.

Device Authorization Grant

Used by devices with limited input capabilities such as smart TVs.

OAuth vs Authentication

OAuth is an authorization framework.

It answers:

What can this application access?

Authentication answers:

Who is the user?

OAuth is often used together with OpenID Connect (OIDC) for authentication.

Common OAuth Security Issues

Open Redirect

Improper validation of redirect_uri may allow token theft.

Token Leakage

Access Tokens exposed in URLs, logs, or browser history.

Insufficient Scope Validation

Applications receiving more permissions than necessary.

Authorization Code Interception

An attacker steals the Authorization Code before it is exchanged.

State Parameter Missing

Can lead to Cross-Site Request Forgery (CSRF) attacks.

What Should a Penetration Tester Check?

• Is redirect_uri properly validated?

• Is the state parameter present and verified?

• Are tokens exposed in URLs?

• Are scopes overly permissive?

• Can Authorization Codes be reused?

• Are Access Tokens properly protected?

• Is PKCE implemented for public clients?
